## Findings

### 1. major — a committed tombstone does not gate `claim_generation_build`, so a tombstoned source can be re-fenced and its failed generation reopened

`src/hippo/store/generations.py:129-186` (`claim_generation_build`)

**Why.** `apply_source_tombstone` leaves the cancelled attempt in `status="failed"`, and
`claim_generation_build` explicitly accepts `"staging" **or** unpublished "failed"` as a
retryable state (`generations.py:140`). It takes no suppression check and no
`source["status"]` check. Verified empirically (PROBE9, fake backend, in-process):

```
receipt fence: 3   cancelled gen: generation-3d48f01e…   status after tombstone: failed
RE-CLAIM SUCCEEDED after tombstone.
  new fence: 4   new active_build_id: maintenancejob-26a4bf02…   gen status: staging
replay now reports fence: 4 (receipt said 3)
```

So after a committed tombstone a caller can (a) take a **new** fence, which is precisely
the thing the plan relies on to make a late worker harmless ("A late worker is harmless
because the source fence … reject[s] writes/publication", plan line 99); (b) install a new
`active_build_id` on a source whose presentation is `deleted/tombstoned`; and (c) run
`_collect_generation` on the never-published attempt (`generations.py:182`) — physical row
removal of exactly the state the plan says stays "retained for recovery/collection"
(plan line 98). It cannot *publish* — `BuildAuthority.check_local` still denies on the
current-only suppression — but invariants 1 ("never enters … generation collect/discard")
and 2 are no longer enforced by the store.

This is also the concrete path that makes the implementer's deviation 7 reachable rather
than theoretical: the replayed receipt's `fencing_token` then reports 4, not the committed 3.

**Scope.** The plan assigns "Tombstoned: return false/not found without mutation" to Task 3's
dispatcher (plan line 129) and `reindex_all`'s preflight (line 131), so PA1 is not in
breach of its own contract. But plan line 135 requires that "a race that converts,
suppresses, changes ACLs, or changes the actor before execution fails safely" — and a
dispatcher re-read followed by a claim is a TOCTOU window, not a barrier. Nothing in
PA1's scope calls `claim_generation_build`, which is why no test caught it.

**Proposed fix** (in PA1's own exclusive file, ~6 lines): in `claim_generation_build`,
immediately after `self._lock_source(gen.source_id)`, refuse when a current-only
`Suppression(target_kind="source", target_id=gen.source_id, reason="tombstone")` exists
— or, cheaper and equivalent for this increment, when
`self.get_source(gen.source_id).get("status") == "deleted"`. Raise the existing
`ValueError("Stale build lease, fence, or generation state")` shape so no new public code
appears. Add one test to `test_managed_source_lifecycle.py`
(`test_a_tombstoned_source_cannot_reclaim_its_failed_generation`) and one to the Ladybug
reopen test. If the orchestrator prefers to keep this in Task 3, then Task 3's brief must
state it as a *store-level* requirement, and deviation 7 should be restated as "reachable
whenever a post-tombstone claim occurs" rather than a theoretical limit.

### 2. minor — disabling on `delete_user` overwrites a non-local `mapping_authority` with `"local"`, destroying the audit record of who granted it

`src/hippo/store/knowledge.py:296-300` (`_apply_local_membership`)

`repaired = existing.replace(enabled=enabled, mapping_authority=LOCAL_MAPPING_AUTHORITY, …)`
is unconditional. On the **enable** path that is exactly what plan step 2 asks for
("Repair an older disabled/different mapping by increasing `policy_epoch`"). On the
**disable** path, plan step 3 asks only to "retain the disabled record as audit state" —
and rewriting `mapping_authority` from, say, `"reviewed"` to `"local"` is the opposite of
retaining it. The behaviour is currently encoded as expected by the edit at
`tests/unit/test_evidence_store_access.py:162-166`
(`membership.replace(enabled=False, mapping_authority="local", policy_epoch=3)` for the
`deleted` case), which is how it passed review. Harmless today because `"local"` is the
only authority this app writes; it silently rewrites provider/group-granted memberships
as soon as those land, and plan line 69 says "Do not infer provider/group memberships".

**Fix.** Keep `existing.mapping_authority` when `enabled=False`:

```python
authority = LOCAL_MAPPING_AUTHORITY if enabled else existing.mapping_authority
if (existing.enabled, existing.mapping_authority) == (enabled, authority):
    return 0
repaired = existing.replace(enabled=enabled, mapping_authority=authority, policy_epoch=existing.policy_epoch + 1)
```

The `test_evidence_store_access.py` assertion above then becomes
`membership.replace(enabled=False, policy_epoch=3)`.

## QUALITY notes on the specific questions the brief asked

**`_set_meta_locked` writing through `type(self).set_meta.__wrapped__` — is any invariant
of `metadata_mutation` lost?** No. `metadata_mutation` (`authorization.py:94-109`) does
three things for `reviewed_mapping_authorities`: validates list-of-nonempty-strings,
takes the authorization lock, and bumps. The caller has already done all three —
`_reviewed_mapping_authorities` (`knowledge.py:317-323`) applies the identical validation
to the value it read, the new value is `sorted(set(read) | {"local"})` so it cannot
introduce a non-string or an empty name, `_lock_authorization` is held by the wrapper
(`knowledge.py:233`) or by `permission_mutation`, and skipping the bump is the entire
point. The `raise RuntimeError` when `__wrapped__` is missing is the right fail-closed
posture. The mechanism is fragile in the abstract (a future `set_meta` override without
`functools.wraps` degrades to a hard error rather than a silent bypass — the safe
direction).

**`_local_mapping_available` skipping on a current store.** It cannot skip on a genuinely
current store. `schema_version()` returns the highest-version row; `migrate_store` leaves
it `(5, "complete")` on success and leaves `_migration_blocked = True` on failure, and
`_ensure_knowledge_ready`/`transaction()` refuse before the helper is ever reached in that
case. Migration *recovery* re-runs `migrate_store` to completion first. What it does do is
skip silently for a pre-v5 store — see findings 3 and 4.

**The decorator's use of the returned user id.** Safe: all three `create_user`
implementations return the freshly generated `user_id` string
(`users.py:237`, `ladybug.py:1931…`, `fake_store.py:871…`). If a future backend returned a
row dict, `_selected_principals` raises `ValueError("Selected principals must be nonempty
identity strings")` inside the mutation's transaction, which rolls the user creation back
— fail-closed, not silent. The remaining smell is that `permission_mutation` dispatches on
`function.__name__ == "create_user" / "delete_user"` string equality
(`authorization.py:74,78,80,85`); a rename or a `functools.partial` wrapper silently
disables the membership hook. An explicit registry or a `@permission_mutation(hook=...)`
parameter would be sturdier, but the existing `had_users or function.__name__ ==
"create_user"` line already established this idiom, so the change is consistent with its
neighbours. Not a finding.

**`apply_source_tombstone` requiring the caller's transaction and locks.** Enforced, not
merely documented — `generations.py:80-82` raises `RuntimeError("Managed tombstone
requires the caller's transaction")` when neither `_transaction_depth` nor `_transaction`
is set, and then takes both locks itself via `_lock_source`.
`test_the_store_primitive_is_unreachable_without_the_callers_transaction` proves it. Two
notes: the check duplicates `build_authority._ambient` (`build_authority.py:160-161`)
byte-for-byte and both should become one shared helper; and it is a backend-attribute
sniff (`_transaction_depth` for Ladybug/fake, `_transaction` for Neo4j), so a fourth
backend that names its flag differently would silently pass the check. Cosmetic.

**The replayed receipt reporting the current fencing token.** Deviation 7 says "if some
later operation fences the source again after the tombstone" — finding 1 shows that
operation exists and is reachable today. Callers misled: any Task 3 retry loop that
compares a replayed `fencing_token` against a stored one to decide idempotency would see
a changed value and could re-dispatch. `suppression_epoch` is the safe field and the
receipt should say so in its docstring.

**Did the four existing-test edits change what those tests prove?** Materially, one did.

- `test_evidence_store_access.py:60` inserts
  `update_knowledge(local_mapping(...).replace(enabled=False, policy_epoch=2))` before the
  first denial assertion, so `test_store_read_requires_explicit_reviewed_workspace_membership`
  now proves "**disabled** membership ⇒ denied" where it used to prove "**absent**
  membership ⇒ denied". That is a necessary consequence of `create_user` now writing a
  membership, and the absent-membership invariant is still covered by
  `test_evidence_access.py:185-206`. Acceptable; worth one comment line in the test.
- `test_evidence_store_access.py:162-166` newly asserts the retained-but-rewritten
  membership after `delete_user`. Accurate to the implementation, but it is what locks in
  finding 2.
- `test_derived_evidence_access.py`, `test_store_knowledge.py` — `put_knowledge` →
  `update_knowledge` with `policy_epoch` 1 → 2 against the same record identity. The
  assertions and the reviewed-authority they exercise (`"reviewed"`, deliberately not
  `"local"`) are unchanged. No loss.
- `test_lookup_snapshot_lifetime.py` — a hand-written `policy_epoch=0` membership removed
  in favour of the one `create_user` writes. Equivalent for access; the test's own
  assertions are untouched.

One behaviour worth recording even though the plan sanctions it (plan step 2 says repair a
"different" mapping): startup rewrites an administrator-chosen non-local
`mapping_authority` for a local User back to `"local"` (PROBE5: `imported` → `local`,
`policy_epoch` 2 → 3), and re-adds `"local"` to `reviewed_mapping_authorities` on every
start (PROBE6: `["imported"]` → `["imported","local"]`). So there is no durable way to
un-map local Users. That is the stated product policy for the single local workspace, not
a deviation — but it means `test_removing_the_reviewed_local_authority_invalidates_a_live_build`
proves an effect that lasts only until the next restart, and any future "disable local
identity mapping" feature has to change this code, not configuration.

Notes for Task 3:
- `tombstone_managed_source` raises `UnmanagedSource` (a `ValueError`) for an unmanaged or
  absent source, `InvalidOperationId` for a bad `operation_id`, and `AuthorizationChanged`
  for every denial **including a reader retrying its own committed delete**. The HTTP layer
  must map `AuthorizationChanged` to the same generic unavailable-source response it already
  uses, never to a distinct "already deleted" response.
- Only `BuildActor.trusted_local()` can ever receive `outcome == "already_tombstoned"`, and
  only for the identical `operation_id`.

  (finding 1).
