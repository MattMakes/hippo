## 3. Findings

### F1 - MEDIUM - six page routes answer a browser with raw JSON when a mapped failure escapes them

`src/hippo/web/app.py:73` (registration), `app.py:115-125` (handler)

`create_app` registers one handler for all five `PUBLIC_FAILURES` families, and that
handler always returns `public_failure_response(...)` - a JSON body. `forbidden_page`, ten
lines below at `app.py:127-138`, negotiates on `Accept` and renders a page for a 403. The
public-failure handler does not, so an HTML page route whose own session raises inside its
`with` block answers `application/json` to a browser.

4b-ii closed exactly this gap for its own four page routes
(`test_managed_web_surfaces.py:429`, `PAGE_SURFACES` = `/graph`, `/changesets`,
`/analyze?question=x`, `/analyze/result-0`) by adding `render.py::public_failure_page`.
4b-i's own page routes were not brought along and are not in that list.

**Failure scenario** (probe 7, `/tmp/hippo-pa4b1-review-7.log`): with `ctx.graph_for`
raising `ProjectionError`, a request carrying `Accept: text/html,application/xhtml+xml`:

```text
GET /                  -> 500 application/json {"error":"Operation failed; ...","code":"operation_failed"}
GET /sources/s1        -> 500 application/json  (same)
GET /account           -> 500 application/json  (same)
GET /ask               -> 500 application/json  (same)
GET /users             -> 500 application/json  (same)
GET /partials/sources  -> 500 application/json  (same)
```

`/partials/sources` is the sharpest of the six: it is polled by htmx, so a transient
projection failure replaces a fragment of the library page with a JSON blob.

Nothing private leaks (`leak=False` on every row), so this is a transport-shape defect, not
a redaction one.

**Proposed fix.** Give `app.py`'s handler the same `wants_html` negotiation
`forbidden_page` already uses and render a generic error page through
`render.py::public_failure_page` with a template that needs no session; keep the JSON body
for `/api/*` and for a non-HTML `Accept`. This is a natural part of the Task 4e dedupe that
`task4-notes.md:18` already schedules for these two modules.

### F2 - MEDIUM - the ask path's traceback is DEBUG-only, and the sentence it prints names an operation ID it never logs

`src/hippo/web/routes/pages.py:110-112`

`failure_text` replaced `log.exception("ask failed")` with
`log.warning("ask failed: %s", type(exc).__name__)` plus
`log.debug("ask failure detail", exc_info=True)`. The server configures
`logging.basicConfig(level=logging.INFO)` (`src/hippo/cli.py:153`), so at the production
default the DEBUG line is never emitted and the traceback is gone.

Meanwhile the sentence the user is handed is `OPERATION_FAILED.message` - "Operation
failed; **inspect local logs by operation ID**" (`public_errors.py:107`) - and the ask path
emits no operation ID at any level. An operator following the instruction in the message
finds one line naming a class and nothing to correlate it with.

**Failure scenario.** `/ask` fails with an unmapped exception in production. The user is
told to quote an operation ID; the operator greps the logs and finds
`WARNING hippo.web.routes.pages: ask failed: RuntimeError` - no traceback, no ID, no
request correlation. Before this slice the same failure produced a full `log.exception`
traceback.

**Proposed fix.** Keep the redaction (the message must not reach the client) but restore
operator visibility: log at WARNING with `exc_info=True`, which goes to the *local* log the
public message already points at and is the level the plan's "Logs may include ... stable
exception class/code" contemplates. If the traceback itself is considered too rich, at
minimum mint and log a bounded correlation ID and include it in the rendered sentence, so
the message stops promising something the system does not provide.

### F3 - MEDIUM - seven JSON failure bodies in `sources.py` carry no `code`, including the two the plan's own table names

`src/hippo/web/routes/sources.py:465, 472, 477, 486, 510, 552, 569`

Enumerated in 2c. Two of the seven are not merely legacy leftovers - the plan's transport
table assigns them a code explicitly:

> | invalid client input/unsupported type/size | `invalid_source` | 400/413 | Existing bounded validation text from closed input validators only |

`too_big`'s 413 (`:472`) and `add_upload`'s unsupported-type 400 (`:477`) are precisely that
row, and the plan adds "Preserve existing response shapes where clients already depend on
them; **add `code`** without returning private details". Keeping the message and adding
`"code": "invalid_source"` satisfies both sentences at once and costs nothing:
`test_legacy_validation_routes_keep_their_own_messages` asserts message substrings, not
body equality, so it stays green.

**Failure scenario.** `RemoteHippo._refusal` (`remote.py:148-153`, the 2026-09-12
remote-client rule) branches in three steps: `code` plus `error` prints `code: message`; a
4xx `detail` prints that bounded text; **anything else** prints the fixed
`operation_failed` sentence and the status. A 413 `{"error": "that upload is N bytes; the
limit is M bytes (HIPPO_MAX_UPLOAD_BYTES)"}` has no `code` and no `detail`, so it lands in
the third branch and the user is told:

```text
operation_failed: Operation failed; inspect local logs by operation ID (HTTP 413)
```

The actionable sentence - which knob to raise - is discarded by the client because the
server did not classify the failure. Adding `"code": "invalid_source"` recovers it, and
the same applies to the unsupported-type 400.

**Proposed fix.** Add `"code": "invalid_source"` to `:472` and `:477`. For the three `Busy`
409s, either mint a closed `indexing_busy` code or route them through
`public_failure_response` with a new row; the messages are already bounded so nothing is
lost. `:465` and `:486` (`add_text`, `add_repo`) are the legacy validators the plan
protects and can keep their present shape, though a `code` would be free there too.

### F4 - LOW - two different `public_failure_page` functions, same name, adjacent modules

`src/hippo/web/app.py:115` and `src/hippo/web/render.py:102`

`app.py` defines `async def public_failure_page(request, exc)` - a Starlette exception
handler returning JSON. `render.py` (after the integration merge) defines
`def public_failure_page(request, failure, template, nav="")` - a page renderer taking a
`PublicFailure` and a template name. `app.py` imports four other names from `render` and
not this one, so nothing is broken today.

**Failure scenario.** The Task 4e dedupe that `task4-notes.md:18` schedules is precisely
"move app.py's local copy onto render.py's". Adding `public_failure_page` to `app.py`'s
existing `from .render import ...` line shadows the module-level `async def` (or is shadowed
by it, depending on order), and `add_exception_handler(failure, public_failure_page)` then
registers a three-argument synchronous page renderer as a two-argument async handler. The
failure surfaces only when an exception actually fires - that is, not in the happy-path
tests the dedupe would be validated against.

**Proposed fix.** Rename one of them before the dedupe: `app.py`'s to
`public_failure_handler` (it is a handler, not a page), or `render.py`'s to
`failure_page_response`.

### F5 - LOW - `add_text` and `add_upload` catch `ValueError` broadly enough to report a managed dispatch error as a caller error

`src/hippo/web/routes/sources.py:463-465` and `:475-477`

`ManagedDispatchError` subclasses `ValueError` (`managed_activation.py:69`), so
`except ValueError: return JSONResponse({"error": str(exc)}, 400)` sits in front of the
closed table for these two routes: a `ManagedDispatchError`, `ManagedConfigurationError`,
`ManagedIngressError` or `ManagedActorRequired` raised synchronously inside
`pipeline.add_text` / `add_upload` would be answered as a 400 blaming the request, with the
exception's own words and no `code`, never reaching `app.py`'s handlers.

I traced reachability and it is **latent, not live** today: `check_actor` cannot fire
because `build_actor_of` returns `BuildActor | None`; `plan_dispatch` cannot raise
`ManagedActorRequired` because a row created microseconds earlier is never `managed`; and
`build_options` / `ingress_file` - the two functions that do raise
`ManagedConfigurationError` / `ManagedIngressError` - are called from `run_managed_build`
inside the background job, not from the route.

This is the same class as the residual `task4-notes.md:42` already tracks for `code.py:217`
and `api.py`, but `sources.py` is not on that list, and the evidence file's audit missed it
by scoping its search to three of the slice's four files.

**Proposed fix.** Re-raise first: `except ManagedDispatchError: raise` above each
`except ValueError`, so the app's closed handlers keep ownership if either error ever
becomes reachable. Two lines, no behaviour change today.

For completeness: the equivalent residual **inside `api.py` is already closed**. The only
two `except ValueError` sites left there at HEAD are `put_settings:50` and
`checked_settings:83`, both true settings validators reached only through
`validate_settings` / `update_settings`, which is exactly what the brief sanctions.

### F6 - LOW / accepted deviation - `delete_source` maps every `AuthorizationChanged` to 404, including a genuine mid-request revocation

`src/hippo/web/routes/sources.py:553-556`

A permission change that happens *while* the tombstone transaction runs is reported as
"no such source" rather than as the 409 the closed table gives every other route. The
plan's non-disclosure requirement ("A retry must not disclose whether an
inaccessible/tombstoned source exists") is what forces this, and the two conditions are
genuinely indistinguishable at this point: `_source_control` deliberately raises the same
`AuthorizationChanged` text for an absent source, a wrong `kind` and a denial
(`build_authority.py:62-67`, confirmed by the pa3b review at `:148`).

Recording as an **accepted, documented deviation**, not a defect. Worth one sentence in the
route's comment saying that the 404 is deliberately wider than "already tombstoned", so a
future reader does not narrow it back.

## 5. Quality review of the five items the brief names

**Can `build_actor_of` produce an actor for a preview or open principal?** No, under any
code path. Detail in 2a: two independent guards for a preview, three for an open principal,
and no preview principal reaches a build site at all because `as_role` is constructed only

control-flow exception, which is what lets the four ingress routes stay declarative.

**`ManagedActorRequired` versus the silent `{"accepted": true}`.** These are two different
conditions and the code keeps them apart correctly: no actor at all over a managed
inventory raises and becomes a 409 (probe 5); an actor that *exists but cannot build* makes
the preflight return `False` and the route answers success. The first is right; the second
is F7's Task 4e obligation. The distinction is easy to lose - both are "the bulk did nothing
for authorization reasons" - and it is worth a sentence in 4e's brief that the two must keep
different codes (`authorization_changed` against `bulk_refused`), because a caller *can* fix
the first by signing in and cannot fix the second at all.

**Does the `test_web_base` adaptation still prove the error is shown, not swallowed?** Yes,
and it is slightly stronger than before. The three assertions that carry the original claim

answer), and the message is present. The adaptation swaps the exception's own words for
`OPERATION_FAILED.message` **and adds** `assert "Neo4j went away" not in response.text` - a
negative assertion the original did not have. The test name still describes what it tests.
Good adaptation.

**Duplicated failure-shape helpers between `app.py` and `render.py`.** Current state: the
