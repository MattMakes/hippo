## Findings

### F1 — Major — `hippo ask` against a running server prints the model's raw reply body

`src/hippo/remote.py:126-127` (4c), root cause `src/hippo/web/routes/api.py:95` and `:115` (4b)

`RemoteHippo._refusal` prints `f"{code}: {message}"` only when the body carries
both keys. `/api/ask` and `/api/search` never send a `code`: they still return
the pre-activation shape `JSONResponse({"error": str(exc)}, status_code=502)`
for an `OllamaError`. `graph.py:347`, `analyze.py:286` and `code.py:204` were
all converted to `public_failure_response(retrieval_failure(exc))`; these two
were not — and `/api/ask` is the endpoint `RemoteHippo.ask()` calls.

`public_errors.py:10-15` names this exact exception as one that carries private
material by construction, and `ollama.py:330,334` confirms it:
`f"Ollama returned HTTP {resp.status_code}: {resp.text[:300]}"`.

**Failure scenario** (`/tmp/pa4c_probe4.py`, reproducing `api.py:95` verbatim
through `httpx.MockTransport`):

```
hippo ask (remote) prints to stderr:
  error: http://server/api/ask: 502 Ollama returned HTTP 500: {'error':'model
  llama3 crashed while reading /Users/alice/private/secret-notes.md: "Zed Labs
  is located in Lisbon"'}
```

An absolute path and a sentence of stored source text on the user's terminal.
The plan is explicit (`rag-it-all-task-5-production-activation.md:194`): tests
"must inject exception strings containing secrets, absolute paths, source text,
and model bodies and assert none reaches logs …, Source rows, JSON, MCP, or
CLI."

**Why the existing test misses it.**
`test_remote_client_never_dumps_a_response_body` injects
`httpx.Response(500, text=...)` — a body `_body()` cannot parse, so it exercises
only the `{}` branch. A *parseable* JSON body holding a raw `error` string is
the case that leaks, and nothing covers it. The `remote.py` docstring's claim
"Nothing else from the body travels" is therefore false as written.

**Proposed fix** — both halves, different owners:

1. *4b's file*: `api.py` `/ask` and `/search` adopt
   `public_failure_response(retrieval_failure(exc))` like the other three route
   modules. This is the real fix and removes the leak at the source.
2. *4c's file, independently worth doing*: `_refusal` must not print a
   code-less `detail`/`error` on a **5xx**. After 4b every server-classified
   failure carries a `code`; a bounded `detail` from a legacy validator is a
   4xx carrying `detail` — FastAPI's validation shape. So restrict the fallback
   to a **`detail` key on a 4xx**, and never fall back to `error`: a code-less
   `error` is the un-migrated route shape and its content is unbounded. That one
   rule closes F6's 409 case too, which `status_code < 500` alone would not.
   Anything else renders as the bare `where` string. Add tests with
   `httpx.Response(502, json={"error": POISON})` and
   `httpx.Response(409, json={"error": "Permissions changed; repeat the query"})`
   asserting `assert_clean` and a stable shape.

### F2 — Major — the four MCP code tools bypass the failure mapper entirely

`src/hippo/mcp_server.py:429`, `:439`, `:413-417`, `:442-472`

`search_tool` and `sources_tool` wrap their whole body in `_answering()`.
`explain_path_tool`, `blast_radius_tool`, `exception_path_tool` and
`history_tool` do not — they call `_code_graph(...)` bare, and inside it
`_code_answer` maps only what `build()` raises. Three paths escape unmapped:

- `_code_answer`'s **leading** `validate()` (`:429`) is outside the `try`.
- `_code_answer`'s `finally: validate()` (`:439`) runs after the handlers, and a
  `finally` that raises **replaces** the mapped `ToolError` already in flight.
- Everything `query_session` does on acquisition and release inside
  `_code_graph` — `ctx.store.get_settings()`, `validate_settings`,
  `query_access`, and the exit-time `validate_live()` (`query_access.py:149`).

**Failure scenario** (`/tmp/pa4c_probe1.py`, `/tmp/pa4c_probe2.py`):

```
  explain_path_tool    -> OllamaError: tok_SECRET /abs/path/x.md 'stored sentence' …
  blast_radius_tool    -> OllamaError: tok_SECRET /abs/path/x.md 'stored sentence' …
  exception_path_tool  -> OllamaError: tok_SECRET /abs/path/x.md 'stored sentence' …
  history_tool         -> OllamaError: tok_SECRET /abs/path/x.md 'stored sentence' …
  search_tool          -> ToolError: retrieval_unavailable: Retrieval service is unavailable
  sources_tool         -> ToolError: retrieval_unavailable: Retrieval service is unavailable
1 leading-validate:  AuthorizationChanged | <poison>
2 trailing-validate: AuthorizationChanged | <poison>
```

Two consequences:

- **The client sees the wrong thing.** mcp 2.1.1 masks an unexpected exception
  (`exceptions.py:50-51`), so the model is told `Error executing tool
  hippo_explain_path` instead of `mcp_server.DENIED`. The *same* condition
  through `hippo path` prints DENIED (`cli.py:199-202`). Item (e) requires them
  to agree.
- **The raw text reaches the server log.** `mcp/server/mcpserver/server.py:440`
  calls `logger.exception("Tool %r raised an unexpected exception")` for
  anything that is not a `ToolError`, writing the full traceback and message.
  Item (e) covers logs.

All `AuthorizationChanged` messages in the tree are bounded constants, so the
authorization case is a consistency defect rather than a leak. The
`query_session`-acquisition case is a genuine leak, since anything
`ctx.graph_for` or the store driver raises goes out with its text.

**Proposed fix** (two lines, no new concepts): wrap all four tools as
`with _answering(), _code_graph(ctx, principal) as (index, theta):`, and move
`_code_answer`'s two `validate()` calls inside the `try` so a validation failure
is mapped like any other — the exact shape, and the ruling on whether that second
half is in contract, are in **F2a** below. Add the `poisoned()` parametrisation
over the four code tools to
`test_mcp_model_failure_is_a_stable_code_with_no_private_text`, and one test
that a denial mid-answer on a code tool reads as `DENIED`.

#### F2a — ruling: does the 4c contract require mapping `_code_answer`'s `finally`?

Asked by the orchestrator mid-review. **Yes — it is in contract, and the two
tests that pin the raw form should be updated rather than the code left alone.**
Both located: `test_lookup_snapshot_lifetime.py:135` (one parametrised case)
and `test_graph_surface_access.py:185` (four parametrised cases, one per code
tool) — five assertions in total. See test updates 1 and 1b below.

The path: `_code_answer` (`mcp_server.py:420-439`) calls `validate()` in a
`finally` that runs *after* the `except Exception -> tool_failure` handler. A
`finally` that raises replaces the exception already in flight, so an
`AuthorizationChanged` raised only there reaches the caller raw. Confirmed at
`/tmp/pa4c_probe1.py` case 2.

**Why it is in contract, not out of scope:**

1. 4c defined the rendering itself. `tool_failure` (`:182-183`) maps
   `AuthorizationChanged` to `mcp_server.DENIED`, and 4c's own
   `test_an_authorization_change_reads_the_same_on_both_surfaces`
   (`test_managed_transport_activation.py:538-558`) asserts `ask_tool` raises
   `ToolError(DENIED)` and the CLI prints the same string. A contract a slice
   writes and pins for one tool cannot be optional for four others in the same
   file.
2. The module docstring 4c added (`mcp_server.py:35-38`) says "**every** tool
   answers with the stable code and bounded sentence", and `_answering()`'s
   docstring says "Whatever goes wrong inside, the client is shown a closed
   public failure". The four code tools are the exception to both.
3. Nothing downstream maps it. `build_server`'s wrappers (`:289-320`) call the
   tool functions with no try/except, and mcp 2.1.1 treats a non-`ToolError` as
   a crash: the model is told `Error executing tool hippo_explain_path` and the
   server writes the full traceback via `logger.exception`
   (`mcp/server/mcpserver/server.py:440`). So the raw form is not "handled
   elsewhere" — it is lost and logged.
4. The `finally` also swallows a **correctly mapped** `ToolError` already in
   flight. If `build()` fails on an `OllamaError` *and* the epoch moved, the
   caller loses `retrieval_unavailable` and gets a masked crash instead.

The HTTP `path` surface in the same parametrisation is different and should
stay raw: `web/app.py:49` registers an app-level `AuthorizationChanged` handler
that renders 409, so raising it *is* that surface's contract. Only the MCP half
is wrong.

**Proposed change** — nest the build so the outer handler sees whatever the
`finally` raises, and bring the leading `validate()` inside it:

```python
def _code_answer(build, validate):
    try:
        validate()
        try:
            return build()
        except (AmbiguousSymbol, UnknownSymbol) as exc:
            raise ToolError(str(exc)) from exc
        finally:
            validate()
    except ToolError:
        raise
    except Exception as exc:
        raise tool_failure(exc) from exc
```

`validate()` still runs on both exits, so nothing about snapshot lifetime or
proof-checking changes. Prototyped and exercised over all eight paths
(`/tmp/pa4c_probe7.py`):

```
ok                         -> returned {'ok': 1}                    (validate 2x)
leading validate denies    -> ToolError: your permissions changed…  (validate 1x)
trailing validate denies   -> ToolError: your permissions changed…  (validate 2x)
ambiguous name             -> ToolError: 'log' could mean any of: a.log, b.log
ambiguous + denial         -> ToolError: your permissions changed…  (denial wins)
model failure              -> ToolError: retrieval_unavailable: …
unknown failure            -> ToolError: operation_failed: …
tool error passthrough     -> ToolError: the question is empty
```

The `AmbiguousSymbol`/`UnknownSymbol` carve-out survives, and a denial
correctly outranks a partially built answer. This is necessary but **not
sufficient** — it does not cover `query_session` acquisition and release inside
`_code_graph`, which needs the `with _answering(), _code_graph(...)` half of F2.
Both are required to close F2.

**Test updates:**

1. `tests/unit/test_lookup_snapshot_lifetime.py:135` — this is the test that
   pins the raw form, via the `surface="mcp_path", action="revoke"`
   parametrisation (`payload` bumps the epoch and then *returns*, so `build()`
   succeeds and only the trailing `validate()` raises — exactly this path).
   Split the assertion by surface the way line 128 already does for
   `action == "error"`:

   ```python
   elif action == "revoke" and surface == "mcp_path":
       with pytest.raises(ToolError) as caught:
           invoke(surface, ctx, request, span)
       assert str(caught.value) == mcp_server.DENIED
   else:
       with pytest.raises(AuthorizationChanged if action == "revoke" else RuntimeError):
           invoke(surface, ctx, request, span)
   ```

   The `surface="path"` (HTTP) case keeps `AuthorizationChanged` for the reason
   above. `assert len(acquired) == 1` and `assert not live_refs(ctx)` both still
   hold: `_answering()` wraps *outside* `_code_graph`, so `query_session.__exit__`
   releases the snapshot before the mapped `ToolError` surfaces.
   **Ownership note:** this file is not in 4c's diff, so amending it needs
   orchestrator routing.

1b. `tests/unit/test_graph_surface_access.py:185` — **the second pin, and the
   more important one.** `test_code_path_surfaces_validate_error_output` is
   parametrised over `operation` × `transport`, so its `transport="mcp"` half is
   **four** cases (`explain_path_tool`, `blast_radius_tool`,


   **Ownership note:** also outside 4c's diff — needs routing.

2. `tests/unit/test_managed_transport_activation.py` — extend
   `test_an_authorization_change_reads_the_same_on_both_surfaces` (or add a

### F4 — Major — gated `hippo index` publishes to everyone and leaves its creator unable to manage it

`src/hippo/cli.py:306`; defaults at `src/hippo/ingest/pipeline.py:133-134`;
rules at `src/hippo/access.py:195-200`, `:111-117`; `min_rank` derivation at
`src/hippo/store/ladybug.py:592` and `store/memory.py:60`

The brief asks directly whether the source is manageable by its creator. It is
not — and the visibility half is worse than the ownership half.

`cmd_index` calls `pipeline.add_upload(ctx, *_upload_for_path(path),
build_actor=actor)` and passes neither `owner_id` nor `access_role_id`, both of
which default to `None`. MCP `hippo_remember` passes both
(`mcp_server.py:502-503`). `access_role_id=None` is copied to
`min_rank: coalesce(r.rank, 0)` = `EVERYONE_RANK`.

**Failure scenario** (`/tmp/pa4c_probe6.py`) — one user, a reader with
`add_sources` but not `manage_sources`, creating the same content two ways:

```
hippo index   : creator may manage = False    rank-0 guest may see = True
hippo_remember: creator may manage = True     rank-0 guest may see = False
```

So `hippo index confidential.md` by a low-rank reader **publishes it to every
role**, while the same text through `hippo_remember` is restricted to the
creator's own tier and above; and the creator can then neither rename nor
delete what they created. Before this slice `hippo index` was ungated and
identity-free, so the widening is not new — but the slice *establishes* the
CLI's identity and then declines to use it for the two fields that decide who
sees the result, which is the point at which it becomes a decision rather than
an omission.

**Proposed fix.** Pass the identity the command already resolved:
`add_upload(..., owner_id=principal.user_id, access_role_id=(None if
principal.is_open else principal.role_id), build_actor=actor)` — exactly
`remember_tool`'s rule, and open mode keeps `None`/`None` as today. Add a test
asserting a gated `hippo index` row is owned by the token's reader and carries
their `min_rank`. If the orchestrator would rather not widen the CLI's
semantics in this slice, the visibility half at minimum needs a decision
recorded, because it is a disclosure and not a convenience.

### F5 — Medium — a bare `ValueError` reads one way over MCP and another on the CLI

`src/hippo/mcp_server.py:188` vs `src/hippo/cli.py:205`

`tool_failure` passes an **exact-type** `ValueError` through verbatim.
`cli._refusal` has no such branch, so for an evidence command the same
exception becomes `operation_failed`.

**Failure scenario** (`/tmp/pa4c_probe3.py`):

```
condition: note.md is too big (9,000,000 bytes); the limit is 1,000,000 …
   MCP  -> note.md is too big (9,000,000 bytes); the limit is 1,000,000 bytes
           (HIPPO_MAX_UPLOAD_BYTES). Split it into smaller parts.
   CLI  -> operation_failed: Operation failed; inspect local logs by operation ID
condition: photo.heic is not a supported file type (text, code, pdf, …)
   MCP  -> photo.heic is not a supported file type (text, code, pdf, docx, epub, html, zip)
   CLI  -> operation_failed: Operation failed; inspect local logs by operation ID
```

To be precise about "before": at `ffd2265` `main()` had no `except Exception`,
so this propagated as a traceback — which at least showed the message. The new
handler is an improvement in shape and a loss in content. Neither surface
produces what the plan's table asks for on this row (`:191`): code
`invalid_source` with "existing bounded validation text from closed input
validators only". `pipeline._check_upload_size` (`:216-221`) and the
unsupported-type check (`:146`) raise bare `ValueError` rather than `TooLarge` /
`ReadError`, so `public_errors._ROWS` never sees them.

**Proposed fix.** Either give `cli._refusal` the same exact-type branch

route it.

### F6 — Medium — an authorization denial reads three different ways on three surfaces

`src/hippo/web/app.py:71-72` → `src/hippo/remote.py:126-127`

The brief asks whether the shared code-less `DENIED` sentence hurts any client.
No client needs to *distinguish* denial from unavailability — the plan keeps a
permission change on "the existing authorization response" (`:191`), and the
CLI/MCP agreement on one string is exactly right. The problem is that the third
surface was not brought along. `/api/ask` has no `AuthorizationChanged`
handler, so the app-level one answers `409 {"error": "Permissions changed;
repeat the query"}` — no `code` — and `_refusal` falls to the legacy branch.

**Failure scenario** (`/tmp/pa4c_probe5.py`):

```
remote CLI : http://server/api/ask: 409 Permissions changed; repeat the query
local CLI  : your permissions changed; check who you are signed in as and repeat the request
MCP        : your permissions changed; check who you are signed in as and repeat the request
```

All three are bounded — no leak — but item (e) requires one shape, and the
remote CLI additionally exposes the internal URL and status for a condition the
user can act on.

**Proposed fix.** Same shape as F1's second half: once a 5xx/409 without a
`code` stops falling through to `detail`, add an `AuthorizationChanged` branch
to `_refusal`, or have `app.authorization_changed` emit the same sentence
`cli.DENIED` and `mcp_server.DENIED` hold. The latter is cleaner and is 4b's
file.

### F7 — Low — MCP `hippo_sources` does not validate its view; the CLI's does

`src/hippo/mcp_server.py:520-542` vs `src/hippo/cli.py:500-508`

`_sources_locally` calls `view.validate()`; `sources_tool` calls neither
`view.validate()` nor `session.validate()`. `query_session`'s exit
(`query_access.py:149`) re-checks the graph proof either way, so the gap is
narrow: `source_view`'s own `authorization_epoch` comparison (`status.py:53`)
never runs on the MCP path. Existing web sites are inconsistent about this too
(`sources.py:95` does not validate; `:489` does), so this is a pre-existing
pattern rather than a regression — but the two surfaces the slice *did* touch
should not disagree with each other.

**Proposed fix.** One line: `view.validate()` before the comprehension in
`sources_tool`, matching `_sources_locally`.

### F8 — Low — `RemoteAmbiguous` can now carry an empty message

`src/hippo/remote.py:111`

Was `detail = response.text` then narrowed by `body.get("detail") or
body.get("error") or detail`. Now `str(body.get("detail") or body.get("error")
or "")`. A 409 that carries `candidates` but neither key produces `""`, and
`cli.main:167` prints a bare `error:` line above the candidate list. Dropping
`response.text` is the right call; the empty fallback is the loose end.

**Proposed fix.** Fall back to a constant — e.g. "that name could mean several
things" — so the line is never empty. `/api/code` always sends `detail` today,
so this is latent.

### F9 — Low — `cli._refusal`'s `AuthorizationChanged` branch contradicts its own docstring

`src/hippo/cli.py:199-204`

The docstring says "An administrative command touches no managed evidence and
keeps its own errors", but the `AuthorizationChanged` check sits *above* the
`command not in EVIDENCE_COMMANDS` guard, so an administrative command would be
mapped to `DENIED` too. No administrative command raises it today, so this is
harmless — but it is the kind of ordering that stops being harmless when
someone adds a capability check to `cmd_settings`. Note also that the two
modules order the same table differently (`tool_failure` checks
`public_failure` first, `_refusal` checks `AuthorizationChanged` first); they
agree only because `AuthorizationChanged` is a bare `RuntimeError`
(`knowledge/access.py:26`) and appears in no `_ROWS` entry. Worth a comment at
minimum.

**Proposed fix.** Move the guard above the `AuthorizationChanged` branch, or
amend the docstring to say a permission change is mapped everywhere on purpose.

## Answers to the brief's specific QUALITY questions

- **`require_online=True` fail-closed on a never-gated deployment.** Exit 2 is
  the right answer and it does **not** break documented open mode. Open mode is
  only reachable when the store answers "no users" (`web/auth.py:169-175`
  distinguishes `None` = unknown from `False` = never gated); a store that
  cannot answer cannot prove open mode, and it could not serve the query
  either. Without `require_online` an unknown state returns
  `Principal.open(top_role)`, handing the top role to a caller that proved
  nothing. The evidence's reasoning here is correct and the message
  (`STORE_DOWN`) is honest about the cause.
- **The shared code-less `DENIED` sentence.** Correct as a design choice; see
  **F6** for the one surface that does not honour it.
- **The exact-type `ValueError` pass-through.** Sound; full enumeration under
  **F5**. Nothing that reaches a client verbatim can carry stored text, a path,
  a token or a model body.
- **`cmd_index` printing the stored error.** Proved *false* for the legacy
  lane; see **F3**.
- **Deviation 2.** Not merely a nicety — it is a visibility widening as well as
  a manageability gap; see **F4**.
- **Transport separation invariants.** Intact. `TransportBoundServer` is
  unchanged, `caller()` still resolves only the selected transport's
  credential, and `test_http_mcp_never_reads_the_process_token` /
  `test_stdio_mcp_does_read_the_process_token` are a genuine matched pair
  (recording environment, positive and negative assertion). The new
  `reader_actor` derives from the principal `caller()` returned and introduces
  no second credential path.

## Changed public signatures (step 4)

**No existing public signature changed** in `remote.py`, `mcp_server.py` or
`cli.py`. Everything is an addition:

- `remote.py`: `PROBE_SECONDS`, `_body()`, `RemoteHippo._refusal()`, attribute
  `RemoteHippo._probe_timeout`.
- `mcp_server.py`: `reader_actor()`, `tool_failure()`, `DENIED`, `_answering()`.
- `cli.py`: `EVIDENCE_COMMANDS`, `NO_TOKEN`, `STORE_DOWN`, `DENIED`, `Denied`,
  `_refusal()`, `_principal()`, `_build_actor()`, `_require()`,
  `_sources_locally()`; `TOKEN_ENV` is newly re-exported from `remote`.

Three **behavioral** contract changes worth recording even though no signature
moved:

1. `RemoteError`'s message format. Previously always
   `f"{base_url}{path}: {status} {detail}"`; now `f"{code}: {message}"` when the
   body carries both, with no URL or status. Anything parsing `RemoteError`
   text breaks.
2. `cli.main()` no longer lets an unknown exception propagate for an evidence
   command — it returns 2 with a mapped message. A caller relying on the
   traceback (or on a non-2 exit) sees different behavior.
3. `RemoteAmbiguous`'s message no longer falls back to `response.text` — see
   **F8**.

## What is good here

Worth saying plainly, because the failures above are concentrated in one
contract and the rest of the slice is careful work:

- The exact-type `ValueError` check in `tool_failure` is the right call for the
  right reason, and the comment explains it. An `isinstance` check there would
  have been a real leak and the implementer caught it.
- `test_http_mcp_never_reads_the_process_token` proving a negative with a
  recording environment, and pairing it with the positive stdio case, is a
  better test than the claim strictly needed.
- `test_cli_code_listing_uses_a_structural_session_not_the_whole_graph` failing
  the test if `ctx.graph()` is touched *at all* is exactly how to pin a "must
  not reach the unrestricted graph" invariant.
- Fixing `remote.py` rather than filtering the `TestClient` warning was the
  correct call, and both branches got a test.
- Deviation 3 (the managed happy path is not exercised through the CLI) is
  flagged honestly rather than papered over, and it is the right thing to have
  flagged — it is where a real deployment first notices the switch.
