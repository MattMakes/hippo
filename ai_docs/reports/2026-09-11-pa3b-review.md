## QUALITY

The dispatch code is good: one classification predicate shared by `delete_source`, `start_indexing`, `run_indexing`, `reindex` and `reindex_all`, so there is exactly one place where "managed or not" is decided and exactly one place to audit. The `eligibility`-versus-`mode` distinction in `delete_source` is subtle and the comment at `pipeline.py:539-540` earns it. The two-loop structure of `reindex_all` makes "all clears before any job" structural rather than incidental. The comments answer *why* rather than restating *what* — `pipeline.py:559-562` (why no `Busy`), `managed_activation.py:366-370` (why ahead of `OllamaError`), `memory.py:31-35` (why only the stage is retired) are all load-bearing.

**Decision 1 — can a managed delete race an in-flight managed refresh?** No. I traced all three directions:

- *Delete lands first, worker later writes the row.* `managed_activation.present` (`:283-303`) takes `store.transaction()` + `store._lock_source` and re-reads the row, returning `False` when `managed_eligibility(source) == "tombstoned"`. That is the same lock `apply_source_tombstone` takes (`store/generations.py:84`), so a late worker cannot overwrite `deleted/tombstoned`. `test_a_managed_delete_does_not_wait_for_its_own_blocked_build` asserts the full row is byte-identical after the blocked worker is released.
- *Delete lands first, worker later tries to publish or claim.* `apply_source_tombstone` bumps `build_fencing_token`, clears `active_build_id`, and marks only that exact unpublished generation `failed` and its exact `MaintenanceJob` `cancelled/source_tombstoned` (`:88-108`) — never the published active generation, never another job. `claim_generation_build` refuses on a committed tombstone at `generations.py:156-160`, before the fence advances and before the retained attempt could be collected.
- *Worker claims first, delete arrives mid-build.* The delete takes the source lock the claim also takes, so the two serialize; whichever loses sees the other's committed state.

Dropping the `Busy` precondition for the managed lane (decision 1) is right, and the reasoning in the docstring is the correct reasoning: `_refuse_if_indexing` exists to protect the orphan sweep at the tail of the legacy delete, a tombstone sweeps nothing and takes no graph write lock, and refusing a withdrawal because an unrelated source is indexing would hold a source readable against invariant 2 and against plan :116. `test_a_managed_delete_suppresses_while_another_source_is_being_indexed` asserts both halves in one test — the legacy delete still refuses — which is exactly how to prove you narrowed a precondition rather than deleted it.

**Decision 2 — not waiting for its own job.** Correct, and `source_lifecycle.py:79-81` says why: cancellation is a courtesy, the fence is the safety mechanism. `CANCEL_WAIT_SECONDS` is not spent. The test holds a refresh inside `/api/chat` and bounds the delete at five seconds.

**`_preflight_managed` and the coordinator's lock discipline** (brief step 3). The preflight captures outside any transaction or source lock and closes the guard on the next line; the coordinator captures and then re-checks `guard.check_local()` *inside* `store.transaction()` + `_lock_source` (`prose_generation.py:474`, `:186-189`, `:200`, `:216`). That is a real difference and it is the correct one: the preflight is advisory by design, and plan :135 requires every worker to recheck authority anyway, which `_install` (`prose_generation.py:471-497`) does. A preflight that took source locks across the whole inventory would be a new lock-ordering hazard for no gain. Worth stating in the evidence, which currently leaves it implicit.

**`_preflight_managed` catching `AuthorizationChanged` only** (decision 4) is right, and the coverage is wider than it looks: `_source_control` (`build_authority.py:62-67`) raises `AuthorizationChanged` — deliberately the same text as the denial — for an absent source, a wrong `kind`, or a missing `workspace_id`, so a source deleted between `list_sources()` and the preflight is handled, not leaked as a crash. Anything genuinely unexpected still propagates rather than being silently reported as "nothing to do", which is the correct bias.

**Decision 5 — raise versus 0.** The *distinction* is well argued (a caller error no retry fixes, versus a runtime condition whose detail must not be disclosed) and both happen before any clear. What is missing is the other end of it — finding 5.

**Decision 6 — an unbounded `operation_id` refused even for an unmanaged source.** Correct: closed input validation on a caller-supplied token, before the lane is known and before any mutation. One asymmetry, finding 10.

**Layering of the sweep constants.** Finding 9. Everything else about the sweep is right, including the choice not to import the pipeline into a store in order to recover from a crash.

**Ownership.** `src/hippo/store/*` is "do NOT touch" in the PA3b brief; the evidence records the orchestrator's written grant for `memory.py`, `ladybug.py` and `fake_store.py` for `mark_interrupted_jobs` only, and the diff honours it exactly — nothing else in those files changed. `web/routes/sources.py` was correctly left alone.

**2. `build_interrupted` is an eleventh managed code, minted in the store layer, outside the closed vocabulary. [MAJOR]**

`src/hippo/store/memory.py:36-40`.

`INTERRUPTED_REFRESH_ERROR` writes `"build_interrupted: The build was interrupted by a restart. Reindex to run it again."` onto a managed Source row's `error`. `status._public_error` reads the code prefix and finds no entry, so the user sees `OPERATION_FAILED.message` — the one actionable sentence the constant carries never reaches anybody. The comment at `memory.py:31-35` claims "the same bounded shape the managed build's own failures use": the *shape* matches, the *vocabulary* does not.

Structurally this is worse than finding 1, because the code is produced by a store rather than by `managed_activation.FAILURES`, so `test_public_errors.py`'s `MANAGED_CODES` table and `test_a_stored_code_and_its_own_exception_agree` are constitutionally unable to cover it — there is no exception to pair it with. **3. The actorless refusal message tells a live managed source apart from a tombstoned one, and calls a delete a rebuild. [MINOR]**

`src/hippo/ingest/managed_activation.py:154` and `src/hippo/ingest/pipeline.py:567`.

A live managed source with no actor is refused inside `plan_dispatch` with `"A managed source cannot be rebuilt without a build actor"`. A *tombstoned* source with no actor returns `Dispatch("skip", "tombstoned")` from `plan_dispatch` (the skip branch at `:151-152` precedes the actor check at `:153`) and is refused one frame later by `_tombstone` with `"A managed source cannot be deleted without a build actor"`. Same exception type, different sentence.

`evidence-pa3b.md`'s delete matrix claims the tombstoned-actorless cell refuses "exactly as a live managed source: an actorless caller cannot tell them apart". That is true of the type and false of the message, and neither test would notice: `test_managed_pipeline_activation.py:1279` and `:1329` both use a bare `pytest.raises(w.module.ManagedActorRequired)` with no message assertion. Separately, "cannot be **rebuilt**" is simply the wrong verb on a delete path, because the refusal comes from the shared classifier rather than from `_tombstone`.

I rate this minor rather than major on exploitability: today the only caller that reaches `delete_source` actorless through HTTP is `web/routes/sources.py:525`, and `manageable_source` denies a tombstoned source from the current view before the pipeline is reached. But "these two refusals are indistinguishable" is a security property the evidence asserts and no test holds, so it is one route change away from mattering.

*Proposed fix.* Give `_tombstone`'s refusal the same sentence `plan_dispatch` raises, and assert `str(exc)` equality across both tests rather than just the type. Do **not** fix it by moving the actor check ahead of the tombstone branch in `plan_dispatch`: that would make `reindex`, `start_indexing`, `run_indexing` and `reindex_all` raise on a tombstoned source with no actor instead of returning skip/False, against plan :129 ("Tombstoned: return false/not found without mutation") and against `test_a_source_tombstoned_between_the_bulk_preflight_and_its_worker_skips_that_lane`.

**4. `reindex_all`'s submission loop can raise after the legacy clears have committed. [MINOR]**

`src/hippo/ingest/pipeline.py:605-610`.

`start_indexing` re-plans (`:254`), and `plan_dispatch` raises `ManagedActorRequired` for a managed source with no actor. In a bulk, legacy lanes are submitted with `plan.actor is None`. If a source that classified as `legacy` at `:594-597` has become managed by the time `:609` submits it, `start_indexing` raises out of `reindex_all` — but `_prepare_reindex` has already committed the clears at `:602-604` and set those rows `queued`. Every lane ordered after the raising one is then a legacy source with no passages, `status=queued`, and no job.

The window is narrow (same thread, no awaits between the loops, and `_refuse_if_indexing` saw no index job), but it is a *new* raise path: the pre-PA3b `start_indexing` could not raise. It also sits awkwardly next to plan :133, which requires one source's failure not to make another's evidence unavailable.

*Proposed fix.* Wrap the per-lane submission so a `ManagedDispatchError` logs and skips that lane instead of aborting the bulk — the same isolation the plan already demands of an asynchronous lane failure:

```python
def _submit(ctx, source_id, plan) -> bool:
    try:
        return start_indexing(ctx, source_id, build_actor=plan.actor, operation_id=plan.operation_id)
    except _managed().ManagedDispatchError:
        log.warning("Bulk reindex skipped source %s: it changed lane after the plan", source_id)
        return False
```

**5. `reindex_all` returns `0` for both "nothing to do" and "refused", and gives Task 4 nothing to map. [MAJOR]**

`src/hippo/ingest/pipeline.py:599`, `:612-627` — `src/hippo/web/routes/sources.py:478-492`.

The brief asks which the HTTP route currently maps and to what. The answer is: **neither, and the two refusals are inverted in loudness.** `sources.py:485` calls `pipeline.reindex_all(ctx)` with no actor and catches only `Busy`; `src/hippo/web/app.py:48-49` registers handlers for `HTTPException` and `AuthorizationChanged` and nothing else. So today, against a managed inventory:

- decision 5's *caller error* (`ManagedActorRequired`, a `ValueError`) escapes the route entirely → unhandled **500**;
- decision 3's *runtime refusal* (failed preflight → `0`) returns **200 `{"accepted": true}`** with a single local `log.warning` (`pipeline.py:625`) as the only trace.

The 500 is Task 4's to remove — plan :220 gives it `web/routes/sources.py` and actor propagation. But the *pipeline contract* is PA3b's, and it hands Task 4 an integer that cannot distinguish "empty workspace" from "one lane's authority failed". Task 4 cannot write a correct route on top of it without re-deriving the state itself.

The evidence states the cost honestly ("a workspace that contains one legacy text source somebody else owns makes an authenticated bulk return `{"accepted": true}` and do nothing at all… an operator has only the local log line to find it by"), and the plan's "no hidden per-source breakdown" (:133) genuinely does specify the `0`. **This is not a SPEC violation** — it is what the plan asks for — but the plan forbids a *per-source* breakdown, not a *global* signal, and the current shape forecloses the latter.

*Proposed fix.* Give the refusal a distinct bounded shape that names no source, so Task 4 can map it to a stable code instead of a lie:

```python
class ManagedPreflightRefused(ManagedDispatchError):
    """One managed lane of this bulk cannot be built; which one is not disclosed."""
```

`_preflight_managed` raises it instead of returning `False`; the route maps it (and `ManagedActorRequired`) to a 409 carrying `OPERATION_FAILED`. `{"accepted": true}` then keeps its meaning: something was accepted. If the orchestrator prefers the literal plan text, the alternative is to keep `0` and require Task 4's route to return 409 when `reindex_all` returns `0` and the inventory was non-empty — worse, because the route has to re-read the inventory to know.

**7. The sweep retires the stage but leaves the orphaned build holder, so the sentence it writes can be refused for up to the lease duration. [MINOR]**
