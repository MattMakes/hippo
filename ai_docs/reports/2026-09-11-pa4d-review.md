### Finding 1 — `ask._dispatch` is imported privately, and its borrow rules differ from the public ones (minor)

`src/hippo/analysis/simulate.py:25`, `src/hippo/evals/runner.py:37`; helper at `src/hippo/ask.py:61-75`.

**Why.** Two modules outside `ask.py` now depend on a private symbol. Decision 5 is right that
copying the three-branch rule into three files would drift, and the precedent (`_answer_from_trace`)
already existed — so this is the lesser evil, not a defect. But the promotion is worth doing early,
because `_dispatch` is not merely `retrieval_session` with a shortcut: its third branch calls
`retrieval_session(ctx, session=session)` and **silently drops `access`**, where
`dense_session._session:178-181` raises `DenseSessionUnavailable("invalid_borrow")` when a caller
supplies both. The two callers that pass both (`runner.py:151` via `_run_all`, and `ask.search` from
`rag_all.py:391-396`) always pass an `access` consistent with the session, so nothing is wrong today;
the point is that the helper meant to standardise dispatch quietly relaxes one of the borrow checks
it wraps. `_dispatch` likewise drops `settings` on the borrowed branches — harmless for `ask`, which
compares them first at `ask.py:83-85`, and contained for `run_question`, which does not compare them
but whose inner `search()` call raises `ValueError` into the per-question handler.

**Proposed fix (for whoever next owns `ask.py`).** Do not add a public alias in `ask.py`. Fold the
pass-through into `retrieval_session` itself, in `knowledge/dense_session.py`, next to the borrow
logic it belongs with: yield the session unchanged when
`type(session) is QuerySession and session.graph.dense_capability.mode in {"verified","tag_compatible"}`.
`ask._dispatch` then collapses to `retrieval_session(ctx, access, settings=settings, session=session)`
and the three importers drop the private import. The promotion must decide two things explicitly:
(i) `access` **and** `session` together — raise (as `_session` does) or ignore (as `_dispatch` does);
(ii) whether the settings comparison at `dense_session.py:182-185` still runs on a pass-through.
Recommend raising on both — but that is not a one-line change, so the promotion must audit every
caller that passes an `access` alongside a `session`. At minimum: `runner.py:106`
(`_run_all` → `run_question`), `rag_all.py:392-397` (`evaluate` → `ask.search`) and
`web/routes/analyze.py:319-327` (the analyze route → `simulate`). Each of those passes an `access`
that is already the session's own, so each can simply stop forwarding it. Note `rag_all.py`
always **owns** its session and never needs the helper itself — see finding 6.

### Finding 2 — `changeset_access.py:170` loads a full unrestricted graph inside the locked mutation transaction (minor)

`src/hippo/knowledge/changeset_access.py:170` (`native_ids = set(self.ctx.graph().node_ids)`).

**Cannot influence a response or a saved record — proven.** Three independent reasons:

1. **It can only refuse, never permit.** `apply` reaches line 170 only after `self.get(identity)`
   (`:166`) has already run `_visible_ops` (`:90-96`) against the **authorized structural** view's
   `idx_of`. Every op target is therefore already proven visible to this audience. `native_ids` is
   the legacy node set; the guard subtracts from what is permitted and adds nothing.
2. **The refusal carries no evidence.** `:177` raises a constant sentence with no identifier
   interpolated. The route (`web/routes/analyze.py:370-371`) maps a bare `ValueError` to
   `HTTPException(400, str(exc))`, so the client sees exactly that constant — checked, not assumed.
3. **It touches neither the written record nor the returned body.** `changesets.apply` (`:179`) is
   called with `(ctx, identity)` only; `native_ids` is never passed on, never stored, and goes out of
   scope at the `with`. The acknowledgement is rebuilt after commit under a fresh `read_scope()`
   (`:185-191`) from `current["ops"]` and the **authorized** `self.graph`, with `graph_version`
   popped at `:180`.

So the audit row's disposition ("confirmed as the audit describes") is correct, and no leak exists.
Two residual concerns remain, neither of which this slice introduced:

* **It is a second, unrestricted, non-structural acquisition inside `store.transaction()` while
  `lock_authorization` is held.** `AppContext.graph()` (`context.py:73-85`) is a different entry
  point from `graph_for`, so it is invisible to both the `watch()` and `order()` recorders, and it
  reloads the *entire* legacy graph from the store when the version has moved — under the write lock.
  Read strictly, plan invariant 4 ("every production query uses structural generation selection")
  does not admit it; the plan's audit section does, as an explicitly classified unrestricted
  operation. The brief's Ladybug line does not reach it, so this review ran it: run d,
  **19 passed, EXIT 0** on `HIPPO_TEST_STORE=ladybug`, with `ChangesetAccess.apply` exercised on a
  managed corpus. No re-entrancy or lock-ordering problem. That result is what keeps this finding
  minor.
* **`ctx.graph()` may be stale by contract.** Its own docstring says a caller that finds a reload
  under way "gets the previous graph". The guard's decision is therefore the only part of `apply` not
  taken against a proof held for the operation's lifetime.

**Proposed fix (not urgent).** Replace the whole-graph load with a narrow store predicate ("is this
node id a native legacy node?") evaluated **before** `self.store.transaction()` opens, or carry the
distinction on the held structural view. Also worth noting: `rg` finds **no test** that makes this
guard fire — the string "Managed evidence requires typed changes" appears only at its `raise`. A test
that applies a changeset naming a managed object id would pin the one behaviour the unrestricted read
exists for.

### Finding 3 — an evaluation run's retrieval failure has no public surface at all, not merely no reason (minor)

`src/hippo/knowledge/eval_access.py:378`, `src/hippo/web/routes/evals.py:53-64`,
`src/hippo/web/templates/partials/run_body.html:42`.

This is the brief's question about the implementer's open finding 2. **Verdict: a gap, not a leak,
and acceptable for this increment — but wider than recorded.**

**Not a leak.** `get_result` sets `result["error"] = None` unconditionally at `eval_access.py:378`,
and `get_run` nulls it at `:424` whenever `authorized[0]` is truthy. That index is `_authorized`'s
`metadata or {}` (`:228`), so the predicate is "the question set carries owner metadata" — true for
every set created through `EvalAccess`, **including** for an internal audience. Only a
metadata-less set read by an internal or open audience keeps its `error`. `_run_all:117`'s
`update_run(error=str(exc))` and `run_question:212`'s `f"{type(exc).__name__}: {exc}"` never reach a
client. Decision 7 is correct.

**Not a gap in the plan's requirements either.** The plan's `retrieval_rebuild_required` row is in
§"Safe transport failures" and binds FastAPI / MCP / remote / CLI responses and managed **build**
failure state; an eval run is neither. The exception-level requirement is met (SPEC c1).

**Wider than recorded.** Evidence deviation 11 says "a reader on the Evals page sees a count and no
reason". A reader does not see a count either:

* `errors` is in `summarize`'s output (`runner.py:266`) but is **not** in `SUMMARY_CARDS`
  (`web/routes/evals.py:53-64`), so the run page never renders it;
* `run_body.html:42`'s per-question `<span class="pill bad">error</span>` is **dead code** on every
  authorized read, because `get_result` has already nulled the field the `{% if %}` tests;
* the only error surface in the template is `run.status == 'failed'` (`:4-5`), which the containment
  in decision 4 guarantees will not fire for a routing failure.

So a run whose every question failed to route renders identically to a run of unanswerable
questions: `done`, blank answers, `accuracy —`.

The pattern is systemic rather than local to runs: `get_question_set` nulls `error` the same way at
`eval_access.py:305`, so `eval_set.html:18`'s "Generating questions failed" callout is dead for the
same audiences. Any fix should carry a closed code through all three readers, not just the run one.

**Proposed fix (Task 4 wrap-up, no owner yet — three parts, all needed).** (i) `run_question` stores
`public_failure(exc).code` in a **closed** field beside `error` (the value is already computed by the
existing pure mapper and carries no private text); (ii) `EvalAccess.get_result`/`get_run` pass that
closed field through instead of nulling it with the raw string; (iii) `web/routes/evals.py` adds
`errors` to `SUMMARY_CARDS` and `run_body.html` renders the code in place of the currently-dead pill.
Part (iii) alone would already remove the silence.

### Finding 4 — the fact-free question-maker corpus narrows the test to the single-hop path (minor)

`managed(ctx, "managed notes")` publishes **one** passage and no facts, so

### Finding 5 — the static RAG-all evaluator's dispatch mode is unobservable by the shared recorder (minor)

`src/hippo/evals/rag_all.py:24,388`.

`rag_all` binds `retrieval_session` from `knowledge.dense_session` directly, while `watch()`
(`test_managed_route_activation.py:102-110`) patches `ask.retrieval_session`. The recorder that gives
"one dispatch, and which route" its meaning for the simulation and the runner is therefore blind to
the third model/dense owner in the slice. What *is* proven for it (run a, pre-existing
`test_rag_eval_session.py`) is one acquisition per evaluated question and release on success, error
and revocation — the more important half.

**This change is conformance with no observable test consequence, and the report should say so.**
Unlike the simulation and the runner, `rag_all` had **no** breakage row: the implementer's baseline
run 0 over `da51784` reported 22 failures that are exactly the 20 Group A + 1 Group B + 1 Group D
rows, none of them in `test_rag_eval.py` or `test_rag_eval_session.py`. Its fixture corpus is purely
legacy, so the plain `query_session` it used to hold already scored. Nothing in the current suite
would notice if this line were reverted. That is not an argument against the change — the plan names
the static evaluator as a model/dense owner and it now is one — but it means the only thing standing
between `rag_all` and a silent regression is the code, so the recorder gap is worth closing.

**Proposed fix — and why the obvious ones do not work.** `watch()` reaches `_dispatch` because
`_dispatch` looks `retrieval_session` up in `ask`'s module dict *at call time*, which is exactly what
`monkeypatch.setattr(ask_module, "retrieval_session", observed)` rewrites. Both `ask.py:33` and
`rag_all.py:24` bind the name at **import** time, so neither re-importing it from `ask` nor patching
`hippo.knowledge.dense_session.retrieval_session` afterwards would be observed. Two fixes actually
work: (i) give `Watch` a second `monkeypatch.setattr` against `rag_all`'s own module namespace, the
same mechanism it already uses for `ask` — smallest change; or (ii) have `rag_all` import the module
(`from ..knowledge import dense_session`) and call `dense_session.retrieval_session(...)`, so the
lookup is deferred and one patch point covers every such caller. (ii) is the better long-term shape
and pairs naturally with finding 1's promotion.

### Finding 7 — `runner.py:209` logs the question text and the full exception (nit, pre-existing, not owned)

`log.exception("Question %r failed", text)` emits the evaluation question and the complete traceback,
including `str(exc)`, at ERROR level. `public_errors.py`'s own docstring notes that `Ollama._request`
"puts 300 characters of the model's reply body into its message", and for a `generated` set the
question text is derived from source passages. The plan's logging rule ("must not include … prompts,
provider response bodies, model output, or unknown exception strings") sits in the managed-build
section, so this is not a Task 4d obligation, and the line is byte-unchanged from before the slice.
Recording it because 4d is what routes a whole-corpus routing failure through this line once per
question. **Proposed fix:** log `type(exc).__name__` and the question **id** rather than `%r` of the
text, and keep `log.exception` for the internal-only lane.

### Checked and deliberately not raised

* **"Empty corpora dispatch more than once" (decision 6) is not a second acquisition.** For an empty
  view `retrieval_session` yields `dense_capability.mode == "legacy"`, which is absent from
  `ask._DISPATCHED`, so each of `run_question` → `search` → `answer_from_trace` re-enters
  `retrieval_session(ctx, session=…)` — three times per question. Every one lands on
  `dense_session.py:186` `nullcontext(session)`: **no** new graph, no profile resolution, no model
  call. `record.once()` in both empty-corpus tests proves one acquisition and one release. Asserting
  the dispatch *set* rather than a count is the honest encoding. Excluding `"legacy"` from the
  pass-through set is also the safer choice, because it keeps the borrow-type and borrow-audience
  checks running on a session the caller might not have acquired structurally. Correct as written.
* **`compare_with_baseline`'s nested owners (decision 8).** The reasoning checks out:
  `BASELINE_SETTINGS` differ from the outer `read_scope()` session's captured settings, so borrowing
  it would raise `invalid_borrow` at `dense_session.py:182-185` — the check exists precisely to stop
  that. Keeping both passes symmetric rather than borrowing on the first and owning on the second is
  the right call for a function whose whole purpose is that the two runs differ only in settings.
* **`_run_all` keeps `query_session` while `run_question` owns the dispatch (decision 4).** Verified
  as a no-regression: before this slice, a `DenseSessionUnavailable` for an unroutable corpus was
  raised inside `search()`, i.e. inside `run_question`'s handler, and was already per-question
  trouble. Moving the dispatch to `_run_all` would have *changed* that contract, not preserved it.
  The chosen shape is the plan's own second option for a model owner and costs no extra acquisition.
* **`changeset_access.py:177` raising a bare `ValueError` rather than `ChangesetUnavailable`.** The
  route distinguishes them (404 vs 400) and 400 is the right status for "these ops are not legally
  editable", so the type choice is deliberate, not sloppy.
* **`_run_all` proving the set before the loop and again inside it.** Two views per run at the
  boundaries of one loop is not the "preflight, close, reacquire for retrieval" pattern the plan
  forbids; the response-bearing work (`run_question` + `save_evaluation_result`) happens under one
  owner. Correct.
* **Decision 13 (no redundant explicit `structural=True`).** Consistent with `query_access.py:76-81`,
  which documents the default explicitly, and with the precedent the 4a audit records for
  `status.py` (cited from `evidence-pa4d.md`, not re-verified here). Adding the keyword would imply
  the default cannot be relied on.
