## Findings

### 1. `major` — first successful `ping()` bumps the authorization epoch and kills a session already in flight
**Out of PA2 scope.** Caused by Task 1, commit `5f6b7e9` "Map live local users into the reviewed
default workspace". Owner: Task 1 (with a Task 4 component).

`tests/fakes/fake_store.py:110` and the real `Store.ping()` (`src/hippo/store/base.py:200-213`,
mirrored at `src/hippo/store/ladybug.py:360`) bootstrap lazily on the **first successful ping**, and
that bootstrap now calls `ensure_local_workspace_memberships()`
(`src/hippo/store/knowledge.py:224-236`), which adds `"local"` to `reviewed_mapping_authorities` and
therefore bumps the authorization epoch exactly once.

**Failure scenario (reproduced).** `web/routes/pages.py:111` opens `query_session(...)`, then
`web/render.py:85` calls `ctx.store.ping()`. If that is the first successful ping, the epoch changes
*inside* the held session and `render.py:101 status_check()` raises
`AuthorizationChanged("Permissions changed; repeat the query")`. Stack captured in
`/tmp/hippo-pa2-review-probe.log`:

```
pages.py:90/111 (ask_page / ask_submit)  ->  render.py:85 ctx.store.ping()
  -> tests/fakes/fake_store.py:110 ensure_local_workspace_memberships()
  -> store/knowledge.py:236 self._bump_authorization_epoch()
```

Observed failures (3, all the same stack):
`tests/unit/test_query_session.py::test_html_ask_uses_one_graph_through_inventory_and_render[True]`
(run c and run d, reproduces in isolation);
`tests/unit/test_answer_original_citations.py::test_answer_surfaces_present_originals_separately_from_ranked_views[html]`
and `::test_search_labels_derived_text_and_analysis_renders_original_evidence` (run e). The `[False]`
parametrisation passes because `ask_page` pings *before* opening the session.

**Why it matters beyond the fake — both real backends are exposed, including the primary one.**
Verified by reading, not inferred from the diff stat:

- **LadybugDB (the plan's primary acceptance backend):** `ladybug.py:357-362` `ping()` calls
  `on_first_connection()` when `not self._bootstrapped`, and `ladybug.py:364-367`
  `on_first_connection` calls `ensure_local_workspace_memberships()` after `ensure_schema` /
  `ensure_roles`. Bootstrap is **not** in `__init__`, so a Ladybug store constructed and then first
  pinged from inside a request has exactly the hazard above.
- **Neo4j:** `base.py:200-218` `ping()` calls `on_first_connection()` on the first successful
  `verify_connectivity()`, and `store/__init__.py:77-81` overrides it to call
  `ensure_local_workspace_memberships()`. `Store.ping()`'s docstring states the intent explicitly
  ("Neo4j may come up minutes after the app and everything still gets set up on the first page
  load"), so the exposure window here can be arbitrarily long after process start.

In both cases the consequence is the same and one-time: the first request after the store becomes
reachable can fail with `AuthorizationChanged` and succeed on retry.

**Gate impact.** `tests/unit/test_query_session.py` is in the PA6 and PA7 CHECK lines. Those lines
will fail as written for this reason, in addition to the AnyIO marker gap the implementer already
recorded.

**Proposed fix (Task 1's call, two options).** The repair is already inside
`on_first_connection`; the problem is that `on_first_connection` itself is lazy, so the bump can land
inside a session a caller already holds. (i) Make bootstrap happen before any reader can hold a
session — ping once at app startup and in the `ctx`/`observed` fixtures, so `render.py:85`'s ping is
never the first one. (ii) If a first-ping bump must stay possible, make the bootstrap path not bump
when the only change is seeding the reviewed authority on an installation with no live users
(`_local_mapping_available()` already gates the rest of the repair), which makes the common
fresh-install and no-user cases fully idempotent.

**Reproduction.** `/tmp/hippo-pa2-review-probe.log`, produced by the read-only pytest plugin
`/tmp/epochprobe.py` (wraps `hippo.store.authorization.bump_authorization_epoch` and prints a stack):
`PYTHONPATH=/tmp HIPPO_TEST_STORE=fake .venv/bin/pytest "tests/unit/test_query_session.py::test_html_ask_uses_one_graph_through_inventory_and_render" -q -o addopts='' -p epochprobe -s`.

### 2. `minor` — `_selected_pairs` scans every authorized revision per selected generation
`src/hippo/knowledge/projection.py:302-310`. The `any(... for revision_id in revisions)` inner loop
makes the function O(selected generations x authorized revisions). For a workspace with ~1k managed
sources and ~10k authorized revisions that is ~10^7 dict lookups per projection, and the projection
runs per request per workspace lane.
**Failure scenario:** a large managed workspace pays a quadratic cost on every structural read; no
incorrect output, only latency.
**Proposed fix:** index `members` once by generation — `selected_revisions` two lines above
(`:362`) already demonstrates the cheaper shape. E.g. build
`by_generation: dict[str, set[str]]` from `members` restricted to `generations`, then test
`any(artifacts[revisions[r].artifact_id].source_id == generation.source_id for r in by_generation.get(identity, ()) if r in revisions)`.

### 3. `minor` — `reindex_all` acquires a structural graph with no owner and no heartbeat (corroborates the implementer's open finding 2)
`src/hippo/web/routes/sources.py:483` and `:489` are the only `source_view(...)` calls in `src/` with
no `session=`, so after this change they take the new `ctx.graph_for(access, structural=True)` path.
`_build_structural_graph` can attach a snapshot bundle whose release is a `weakref.finalize`
(`context.py:424-429`) and whose lease renewal normally comes from `query_session`'s
`LeaseHeartbeat` — neither applies here.
**Failure scenario:** a managed corpus with a strict manifest, plus a `pipeline.reindex_all` that
runs longer than the snapshot lease, makes the post-operation `view.validate()` raise and the route
return 500 rather than `{"accepted": true}`; the lease itself is released only at GC.
**Proposed fix:** as the implementer records, Task 4 / PA5 must give `reindex_all` a held owner whose
lifetime spans its post-operation `validate()`. This review confirms the call sites and the
mechanism; nothing needs to change in PA2's files.

### 4. `minor` — code-edge attribution for a shared node is by node membership, not by exact pair
`src/hippo/status.py:104-109`. `nodes` now includes nodes a source contributed via
`structural_code_evidence` / `structural_object_evidence`, and `edge_counts` then counts every
`CODE_EDGE_KINDS` arrow in `graph.code_out` whose source vertex is in that set. Unlike the relation
count immediately below it (`:112-116`), which is gated on `pair in row.source_generations`, this has
no per-pair provenance check.
**Failure scenario:** a symbol contributed by generations of sources A and B, where only A's
generation produced the outgoing `INVOKES` edge, reports that edge in B's
`meta.code.edges_by_kind` too. Practically unreachable today — a managed prose lane emits `PREDICATES`
arrows, not `CODE_EDGE_KINDS` arrows, and the two vocabularies are asserted disjoint by
`test_relation_predicates_cannot_be_counted_twice_as_code_edges` — so this is a latent gap that
becomes real when Task 6+ adds managed code generations.
**Proposed fix:** either carry a per-pair provenance set for inherited code edges and gate the
counter the same way the relation counter is gated, or add an explicit comment at `:104` recording
that inherited code edges are attributed by node membership and why that is currently exact.

### 5. `minor` (coverage) — a relation supported by two generations is not tested
`tests/unit/test_managed_source_inventory.py:414-428` is the only relation test, and
`shared_pair(..., relationship=True)` builds its `AssertionSupport` from a single generation's span,
so `source_generations` always has exactly one entry. The multi-contributor branch of
`pair in row.source_generations` is therefore never executed, even though the brief's adversarial
case (plan line 254) names "one relation support from multiple generations".
**Failure scenario:** a future change to `StructuralRelationEvidence.source_generations` ordering or
to the membership test would not be caught for the two-contributor case.

### 6. `minor` (coverage) — `compose_graphs`'s `populated` shortcut version is not asserted
`src/hippo/knowledge/projection.py:1046-1048`. The fix (a pair-only lane counts as populated, so a
single-lane composition cannot inherit a different lane's `version`) is exercised only for the pair
tuple, not for `result.version`. The consequence is visible only for an `internal` audience, where
`_build_managed_graph`/`_build_structural_graph` do not overwrite `version` with
`view_fingerprint(...)`.
**Failure scenario:** an internal-audience composition of one empty legacy lane plus one pair-only
managed lane silently reports the legacy lane's version if the `or graph.selected_managed_generations`
clause is ever dropped; nothing fails.
**Proposed fix:** add one assertion to
`test_compose_unions_pairs_and_refuses_two_generations_for_one_source` that
`compose_graphs(lane(()), lane((pair,))).version` equals the pair-only lane's version and differs
from the empty lane's.

### 7. `minor` — canonicalisation raises bare `ValueError` where its neighbours raise `ProjectionError`
`src/hippo/hipporag/graph_index.py:205` and `:210` raise `ValueError`. They surface through
`_assemble` and `compose_graphs`, whose own failures are `ProjectionError` (a `ValueError` subclass).
A caller writing `except ProjectionError` — the documented projection-failure contract — will not
catch a duplicate-source composition, while `except ValueError` catches both.
**Failure scenario:** a Task 4 route that maps `ProjectionError` to a stable public failure lets a
`ValueError` escape as an unmapped 500 instead. The new test deliberately asserts only
`pytest.raises(ValueError)`, so either behaviour passes.
**Proposed fix:** leave `graph_index.py` alone (it must not import from `knowledge`) but have
`compose_graphs`/`_assemble` wrap the construction and re-raise as `ProjectionError`, or document at
`compose_graphs` that a lane-consistency failure is a plain `ValueError`.

### 8. `minor` — status and MCP identity now do structural loading on every call
`src/hippo/status.py:242` (`_audience_inventory`, session-owning branch) and therefore
`visible_source_count` (`:269-273`) and `system_status(..., session=None)`. This is the orchestrator's
recorded decision and is required for the counts to agree with `source_view`, so it is correct — but
it changes the cost profile of the most frequently hit endpoints: structural loading reads evidence
sidecars and, for strict manifests, acquires and releases snapshot leases per call. `system_status`
caches only the health block (`CACHE_SECONDS = 8.0`); the inventory is recomputed every request by
design.
**Failure scenario:** a status-polling UI on a managed corpus with strict manifests generates one
snapshot acquire/release pair per poll per audience.
**Proposed fix:** none required for PA2. Worth a line in the Task 4 brief so the structural default
flip is measured rather than discovered, and so route owners that already hold a session keep passing
it (they all do today except `reindex_all`, finding 3).
