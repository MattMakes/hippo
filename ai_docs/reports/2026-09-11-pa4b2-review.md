## 3. Findings

### 1 — MEDIUM — an activation failure at acquisition escapes the graph-browse JSON routes unmapped

`src/hippo/web/routes/graph.py:196` (`full_graph`), `src/hippo/web/routes/graph.py:432`
(`node_details`); same class at `analyze.py:63`, `analyze.py:119`, `analyze.py:244` and
`render.py:118` for the HTML pages.

**Why.** `GraphIndex.__post_init__` (`graph_index.py:278`) calls `canonical_selected_generations`,
which raises a **bare `ValueError`** (`graph_index.py:209,212`). It fires during
`ctx.graph_for(...)`, i.e. inside `query_session`, i.e. inside the `with` these routes open with no
mapper around it. `ProjectionError`, `DenseUnavailable` and `QuerySnapshotUnavailable` are all
`ValueError` subclasses and reach the same place. `light_up` and the five `/api/code/*` endpoints
map it; their five neighbours in the same two files do not.

The brief's requirement is "cannot escape a route unmapped", and the plan's "Safe transport
failures" table gives `operation_failed` / 500 for an unknown query exception. It escapes.

**Failure scenario** (probe 5, `/tmp/hippo-pa4b2-review-3.log`, measured):

```
POST /api/graph/light-up     -> 500 [application/json] {"error":"Operation failed; …","code":"operation_failed"}
GET  /api/code/symbols?q=…   -> 500 [application/json] {"error":"Operation failed; …","code":"operation_failed"}
GET  /api/graph/full         -> 500 [text/plain] 'Internal Server Error'
GET  /api/graph/node/{id}    -> 500 [text/plain] 'Internal Server Error'
GET  /changesets             -> 500 [text/plain] 'Internal Server Error'
GET  /graph                  -> 500 [text/plain] 'Internal Server Error'
GET  /analyze?question=x     -> 500 [text/plain] 'Internal Server Error'
```

Two sources with an active generation each on one `source_id` — the exact composition mistake
`canonical_selected_generations` exists to catch — takes the whole Graph page and its browse API
to a bare Starlette error. The page's own JavaScript reads JSON from `/api/graph/full` and
`/api/graph/node/{id}`; a `text/plain` body is not the `{error, code}` shape the Task 4 cross-part
contract promises "on every route", so a client cannot branch on it.

**Severity MEDIUM, not HIGH.** `ServerErrorMiddleware` runs with `debug=False`, so
`"SELECTED GENERATION INTERNALS"` appears in none of the responses. Nothing private leaks; the
shape contract and the ability to distinguish "rebuild your sources" from "we broke" do.

**Proposed fix.** Give `full_graph` and `node_details` the mapper `light_up` already has — they are
in the same file and already import it:

```python
try:
    with query_session(ctx, principal.access) as session:
        ...  # unchanged body
except (ValueError, OllamaError, httpx.TransportError) as exc:
    return public_failure_response(retrieval_failure(exc))
finally:
    validate_viewer()
```

`AuthorizationChanged` is a `RuntimeError` and stays uncaught, so the 409 still wins — the same
argument `graph.py:345` already records. For the three HTML pages the honest minimum is an
`except` that renders the bounded sentence the way `analyze_submit` now does (`analyze.py:104-108`);
a JSON body on a page route would be worse than the status quo. If the orchestrator would rather
accept the deviation than spend the edit, the decision belongs in the gate ledger and not in
silence, because "one public body for the whole web layer" (`render.py:8-10`) is not true while
five routes in the same two files skip it.

### 2 — LOW — `_answer`'s `except ValueError` shadows the public mapper by type, not by intent

`src/hippo/web/routes/code.py:216`.

`_code_response` (`code.py:192`) documents "the two failure vocabularies kept apart": `_answer` maps
what the caller got wrong, the outer `except` maps what went wrong with the view. But `_answer`
runs **inside** the outer `try` and catches `ValueError` (`code.py:216`) → `HTTPException(400, str(exc))`.
`ProjectionError`, `DenseUnavailable` and `QuerySnapshotUnavailable` are `ValueError`s. The
separation therefore holds by **timing** — every one of them fires at acquisition, before `build()`
— and not by type. The day a payload builder touches a lazily-composed graph path, an incoherent
view becomes a 400 that blames the request *and* prints the exception's own text.

**Fix.** Give `_required` (`code.py:174-179`) its own exception (`class BlankArgument(ValueError)`
or a `LookupError` sibling of `UnknownSymbol`) and have `_answer` catch that instead of bare
`ValueError`. Two lines, and the claim in the docstring becomes structural.

### 3 — LOW — `code.py`'s catch tuple omits `httpx.TransportError`

`src/hippo/web/routes/code.py:203` catches `(ValueError, OllamaError)`; `analyze.py:104`,
`analyze.py:283` and `graph.py:344` all catch `(ValueError, OllamaError, httpx.TransportError)`.
`public_errors._ROWS` lists `httpx.TransportError` (`public_errors.py:100`) precisely because the
model client is httpx and a connection error can escape unwrapped. No code endpoint calls a model
today, so this is unreachable — but the four sites are meant to be one rule, and three of them
spell it one way. Add the third member.

### 4 — LOW — `light_up`'s pre-validation duplicates `query_session`'s settings merge verbatim

`src/hippo/web/routes/graph.py:337` is character-for-character
`query_access.py:124`'s `validate_settings({**ctx.store.get_settings(), **(settings or {})})`.
The duplication is **justified** — without it, a bad slider value would arrive at
`retrieval_failure` as an ordinary `ValueError` and answer 500 `operation_failed` instead of 400,
which is the very confusion `graph.py:333-335` sets out to prevent. The problem is that the two
copies are only correct while they stay identical, and nothing makes them. A shared
`effective_settings(ctx, settings)` in `query_access.py`, called by both, removes the drift without
changing a single response.

### 5 — LOW — the 400 pre-validation can quote an operator's stored setting and blame the caller

`src/hippo/web/routes/graph.py:340` raises `HTTPException(400, str(exc))` on the merged dict. If a
*stored* setting is out of range, `validate_settings` (`store/base.py:92`) produces
`"<key> must be between <low> and <high>, got <value!r>"` naming a value the caller never sent, and
light-up answers 400 as though the request were at fault. Settings are numeric knobs, so nothing
secret is disclosed, and every write path validates, so this needs a store edited out of band. Low
likelihood, trivial consequence; recorded because the same line is the slice's own 400/500 boundary.

### 6 — LOW — the HTML analyze form answers HTTP 200 for every mapped failure

`src/hippo/web/routes/analyze.py:108` renders with `render`'s default `status_code=200`, so a
`retrieval_rebuild_required` (409) and a `retrieval_unavailable` (503) are both a 200 page carrying

should stay 200 deliberately, that is worth one sentence in the evidence file.

### 7 — LOW (latent) — `retrieval_failure`'s total fallback would swallow an authorization denial

The brief asks for the enumeration, so here it is in full.

`retrieval_failure(exc)` = `public_failure(exc) or OPERATION_FAILED` (`render.py:85`). It yields
`OPERATION_FAILED` for:

* **explicitly**, from `public_errors._ROWS`: `BuildBusy`, `BuildCancelled`, `ProjectionError`;
* **explicitly**, from `public_errors.py:151`: `DenseSessionUnavailable` with `reason == "invalid_borrow"`;
* **by fallback**: every exception not in `_ROWS` at all. Restricted to what the routes' catch
  tuples admit — `ValueError`, `OllamaError`, `httpx.TransportError` — the fallback set is the
  `ValueError` subclasses the table does not list: `ManagedDispatchError`, `RepoError`, `Busy`,
  `_StorageFailure`, `_ChangedInput`, `EmbeddingMismatch`, `QuerySnapshotUnavailable`,
  `RawArtifactError`, `SourceLifecycleError`, `ChangesetUnavailable`, `EvalAccessDenied`,
  `SnapshotUnavailable`, `GenerationCountsUnavailable`, and bare `ValueError`.

**Is any of them an authorization type? Today, no.**
`AuthorizationChanged` is a `RuntimeError` (`knowledge/access.py:26`) — a *sibling* of `OllamaError`,
not a subclass — so no catch tuple in the slice admits it, and `graph.py:345` says so. I checked
that no layer wraps it into a `ValueError` on the way out: `dense_session._classification`'s
`except ValueError` (`dense_session.py:118`) sits below an `owner.validate()` that is outside the
`try`, and its `finally` at `:122` re-raises the authorization error over any mapped one.

Two `ValueError`s in the fallback set *are* denial vocabulary — `EvalAccessDenied` ("unknown …or
access denied") and `ChangesetUnavailable`. Neither is reachable: `light_up` touches neither, and
`_simulate` (`analyze.py:296-300`) calls only `EvalAccess.get_result`, a `_guarded_item`
(`eval_access.py:344`) that returns `None` on denial and is converted to the route's own 404. The
hazard is that `_simulate` constructs an `EvalAccess` **inside** the mapped scope, so the first
unguarded `EvalAccess` call added there turns "access denied" into a 500 `operation_failed`. Worth
one line in `_simulate` or an `except EvalAccessDenied` ahead of the mapper in `simulate`.

## 4. Quality review of the five items the brief names

**The two-audience `graph_page` preview branch (decision 3) — no cross-audience leakage, either
direction.** Measured (probe 7): `/graph?as_role=individual` acquires two owners, released LIFO, and
their audiences are `('preview', rank 0, user_id=None)` for the page body and
`('reader', rank 40, <actor's id>)` for the header. `render` is handed `session=None` in this branch
(`graph.py:167`) and so re-derives its status from `context["me"]`, which `render.py:111` defaults to
`request.state.principal` — the **actor**, never the previewed principal. The header therefore cannot
show the previewed tier's evidence. The reverse direction is closed by rank: `viewer` refuses a role
whose rank exceeds the actor's (`graph.py:88`) and the menu only offers `r["rank"] <= actor.rank`
(`graph.py:163`), so a preview is always a downgrade and its body is a subset of what the actor may
already see. Decision 3 is sound, and recording it rather than quietly keeping it was the right call.
The two live owners are a real cost (two snapshot leases, two heartbeats for one response) but
merging them would, as the decision says, print one audience's counts over the other's graph. The
one thing the decision does not say is finding 8.

**The verified-lane web cases as direct route calls (decision 6) — a real HTTP-level gap, correctly
