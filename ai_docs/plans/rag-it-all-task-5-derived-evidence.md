# Task 5 derived retrieval evidence proposal

Status: storage slice implemented and independently reviewed; evidence is in `ai_docs/gates/rag-it-all/task-5-derived-store/GATES.md`. Reader/projection and production integration remain separate pending work. This narrows the original/derived Passage and ProseExtraction decisions in `rag-it-all-task-5-pipeline.md`; it does not replace its lifecycle, profile-resolution or parity gates.

## Decision and boundary

Use the existing `RetrievalView`, `DerivedRecord` and `DerivedDependency` contracts for rendered text and provenance. Add one nullable native Passage column, `retrieval_view_id`, and one registered immutable record, `ProseExtraction`, with a closed nested output payload. Extend exact membership to that record. No new engineering assertion predicate, global Fact authority or synthetic EvidenceSpan is needed.

An original dense row continues to embed exactly its EvidenceSpan text. A rendered dense row embeds exactly an explicitly selected RetrievalView text and retains its anchor span/revision plus every original dependency. Inference input may be a separate view: a symbol documentation extraction must not silently use its generated signature/body card as OpenIE input. Citations always resolve to original spans and actual locators.

This is a schema 5 change because native row shape and registered knowledge tables change. Existing legacy and strict schema 4 generations keep their identities, seals and serving semantics. New production builds opt into a versioned derived-evidence capability through their captured generation configuration; migration does not infer missing provenance.

## Controlled capability boundary

Root approved the review refinement: the first controlled schema5 exact membership of RetrievalView, DerivedRecord, DerivedDependency or ProseExtraction stamps `Generation.coverage_json["derived_evidence_version"] = 1`. Ordinary callers cannot preseed the reserved key, downgrade it or remove it. The evidence checksum commits this marker. `derived_capability(generation)` exposes the same boundary to readers; `validate_view` and `validate_prose` require it. Sealing validates every selected view and complete derivation child group, including unbound views and orphan derivations. Historical v4 unbound view metadata keeps its original contract and checksum because it has no marker.

The helper return is a frozen `DerivationClosure` with `span_ids`, `revision_ids`, `derived_record_ids`, `dependency_ids`, `view_ids`, `binding_ids` and `support_passage_ids` frozensets. It establishes exact provenance only, never an audience grant. The fenced writer may call `validate_prose(..., require_member=False)` before inserting the candidate's exact membership; all reader calls use the default true.

## Rendered-view lineage without new view columns

A new strict rendered view requires:

- The anchor `span_id` is an exact EvidenceSpan member, and its revision equals `source_revision_id` and belongs to the selected source's raw generation manifest.
- `derived_record_id` selects a ready, exact DerivedRecord in the same workspace. Its declared input revisions equal the transitive original revision inventory; its binding inventory, if used, equals its binding dependencies. Every input remains inside this source generation for the initial implementation.
- At least one original span dependency exists, including the anchor. Every original contributing span is listed; an anchor is not a substitute for other inputs. All DerivedDependency rows for the record must be selected, not merely a convenient subset. For the initial production writer allow revision/span/binding inputs only; reject other existing dependency kinds for this capability until their full projection/temporal semantics are implemented. Bindings must themselves be generation-owned and have exact original/observation closure.
- Define a versioned, canonical dependency fingerprint over the purpose, view kind, rendering rule/profile versions, model version if any, sorted typed `(input_kind, input_id, input_version)` tuples, and `text_hash(view.text)`. The fingerprint must be equal on RetrievalView and DerivedRecord. The hash excludes record IDs that themselves depend on the fingerprint, avoiding circular identities. Input versions refer to immutable record content fingerprints, not mutable timestamps. A policy grant is re-evaluated separately and never treated as immutable access authority.
- `view.derivation_version == derived.rule_version`, compatible view kinds, and exact text/vector profile agreement with the captured build configuration. `view.vector_profile == generation.embedding_profile` for dense views. The opaque generation profile alone does not replace resolved embedding dimension and prefix identity verification.

RetrievalView identity already includes its dependency fingerprint, so binding the output text hash into that fingerprint makes changed rendered text produce a new view identity without changing old record identities or adding a text-hash column. The writer must compute this recipe centrally; the store must recompute it. Existing write immutability alone does not establish that a caller supplied a correct fingerprint.

For a rendered Passage require its view as an exact generation member, matching anchor revision/span, text exactly equal to view.text, embedding profile equal to view.vector_profile and the generation profile, and the canonical view-aware passage ID. Store original spans unchanged. Require finite nonempty float32 vectors with the same dimension as all other representations. Every post-seal mutation of binding, view text, dependency group or derived state must fail; adding a new dependency to a sealed derivation is prohibited just as adding support to a published assertion group is prohibited today.

## Closed inferred prose payload

Add frozen nested Contracts and one Record; nested values serialize using the existing `_json_field` path into canonical JSON storage. Do not accept arbitrary dictionaries, arbitrary JSON keys, embeddings in RetrievalView.text or raw global Fact IDs.

| Field on ProseExtraction | Type / invariant |
| --- | --- |
| `generation_id` | Nonempty Generation ID; source/workspace are derived through Generation and its Source, then compared with the derivation workspace. |
| `derived_record_id` | Exact ready DerivedRecord; `view_kind='projection'`, rule/model versions identify the captured extractor/cleanup process. |
| `input_kind` | Closed Literal `span` or `view`. |
| `input_id` | Dynamic typed reference to EvidenceSpan or RetrievalView, selected in the same generation. |
| `input_text_hash` | Hash of the exact referenced text sent to extraction, before any model-specific wrapper declared by extractor profile. |
| `support_passage_ids` | Nonempty, sorted, unique tuple of native Passage IDs explicitly supported by this input; every row belongs to this generation and has verified original/view binding. |
| `extractor_profile` | Resolved extraction model/prompt/schema/cleanup/settings fingerprint. |
| `embedding_profile` | Same captured profile as Generation and the output vectors. |
| `payload` | `ProseExtractionPayload`, below. |
| `payload_hash` | Computed/validated hash of the canonical nested payload after deterministic float32 normalization. |

Identity fields: `(generation_id, derived_record_id, input_kind, input_id, input_text_hash, support_passage_ids, extractor_profile, embedding_profile, payload_hash)`. All fields are immutable. Creation/observation timestamps and output payload never enter Generation's accepted-input identity. An identical-input retry may produce a different extraction identity; it must replace the failed attempt's selected inventory under its fresh fence.

`ProseExtractionPayload` has `schema_version: Literal[1]`, `evidence_class: Literal['model_inferred']`, `entities: tuple[ProseEntity, ...]`, and `triples: tuple[ProseTriple, ...]`. `ProseEntity` has normalized nonempty `name` and `embedding: tuple[float, ...]`. `ProseTriple` has normalized nonempty `subject`, `predicate`, `object`, and its fact `embedding: tuple[float, ...]`. This payload represents only successful extraction, including successful empty output. Skips and failures belong to the build's declared coverage outcomes; they are not empty successful records.

Canonicalization uses the captured existing cleanup rules, deduplicates entity names and triple tuples, and sorts deterministically. Include all triple endpoint names in entities, with vectors when required by the legacy entity channel. Embeddings are finite, nonempty, float32-canonical values of the captured dimension; reject booleans, NaN/infinity, mixed dimensions and incompatible profiles. Fact embedding input is exactly the current indexer's documented triple-rendering rule captured in the profile. Model evidence remains inferred even when a predicate happens to spell a registered engineering predicate.

For span input the derivation selects that original span and revision. For view input it selects every original dependency of that view; `input_id` supplies the explicit typed view edge, so no new DerivedDependency input kind is necessary. If extraction text differs from an existing span/view, create a separate honest extraction-input RetrievalView with full original lineage. Do not change `input_text_hash` to excuse a mismatch.

Add support_passage_ids to typed list references targeting Passage. Each support row must have original dependency coverage consistent with the extraction input: its verified original dependency set must include the extraction input's original span dependencies (the prepared reader mapping must expose a documentation subspan explicitly when needed). Authorize the support passage's entire original closure as well, including context not sent to extraction. Reject an unrelated passage even in the same generation. These explicit links preserve the existing logical chunk contributions and avoid guessing support from an anchor or a shared Fact. Multiple view vectors of the same logical chunk do not automatically become extra support; the staged writer chooses the declared support passages in PreparedIndex.

The extraction DerivedRecord uses a separate versioned fingerprint recipe committing its sorted original dependency tuples, input kind/ID/hash, support passage IDs, extractor and embedding profiles, and payload_hash. None of those values contains the extraction DerivedRecord ID, so this also avoids circular identity. The store recomputes the recipe.

Only one successful ProseExtraction is selected per `(generation_id, input_kind, input_id, extractor_profile)`. Conflicting results must fail sealing rather than union nondeterministic model outputs. Allow many input records with shared normalized names/triples; their distinct passage support remains visible and countable.

## Closure, sealing, lifecycle and retention

Implement one shared closure walker with cycle detection and explicit supported kinds. Treat a dependency row's owner reference as structural bookkeeping, not a cyclic derivation input. Traverse Passage references through their native generation/revision/span/view binding explicitly: the existing `_record_revisions` only recurses into registered knowledge records and therefore cannot validate native support references alone. Forward references from RetrievalView to its DerivedRecord do not enumerate the DerivedDependency children today: sealing must explicitly enumerate and require the complete child set. Check full child groups before recursion, derive the original span/revision set and compare both directions against declared inventories. Reject missing inputs, foreign generation/source/workspace, incomplete exact membership, conflicting hashes/profiles and newly appended dependencies on a sealed derivation. Never infer exact interpretation solely from raw revision membership.

Include ProseExtraction's typed payload and all selected lineage in the existing evidence checksum; include view-bound Passage rows in dense. Validate all prose vector dimensions/profiles alongside native dense/code vectors during checksum construction. Preserve mandatory representation keys `evidence`, `dense`, `native`; this small change does not require a fourth representation key or alter the schema 4 manifest contract. The production capability's canonical coverage descriptor must additionally enumerate expected dense views and expected extraction inputs/outcomes. The coordinator checks that inventory against PreparedIndex and actual selected records before sealing. A missing requested extraction fails the initial parity build, even when dense coverage is present; an explicitly skipped input follows the recorded extract_text/minimum-length policy.

These records use ordinary generation_write lease/source fencing. Add ProseExtraction to write membership guards and the exhaustive content-epoch classifier. Derivation state changes affecting published payload cannot use generic mutable lifecycle fields to evade sealing. Policy/suppression changes retain their existing authorization invalidation semantics; payload writes do not create grants. No model calls happen under the write transaction.

Collection remains conservative: an active generation or unreleased active/saved snapshot blocks collection of its complete derived closure. Removing collectible native rows also removes their view bindings; retained exact provenance never permits serving a failed/collected generation. Keep shared EvidenceSpan, RetrievalView, DerivedRecord, DerivedDependency and ProseExtraction payloads rather than add an unproven eager delete sweep. Ever-published exact-member tombstones preserve lifetime immutability; never-published cleanup may remove its exact membership so a fenced retry selects a fresh output. Retained orphan payloads are harmless unavailable data, not a current inventory. Future payload/blob reclamation must use reverse reachability across generations, derived dependencies, history and saved snapshots; an anchor-only walk is insufficient.

## Authorization and projection changes

`AuthorizedEvidence` gains frozen `derived_record_ids`, `derived_dependency_ids`, `retrieval_view_ids` and `prose_extraction_ids`; include them in the proof fingerprint. `_interpretation_inventory` must select the new kinds and existing derivation kinds from exact membership before evaluating ACLs. Do not introduce a legacy fallback for an empty strict inventory.

After original span grants are known, authorize a derivation only when every original input span/revision is authorized and every typed intermediate is selected, complete and ready. Apply `Suppression(target_kind='derived_record')` to both the view and extraction derivation; propagate an input view's suppression to its extraction. Workspace, source access, provider freshness, historical/current applicability and earliest policy deadline still intersect. One hidden secondary input denies the whole rendered view/extraction, including labels, vectors, counts and synonym candidates. Current permission revalidation remains mandatory after model work and before release, even with a retained generation snapshot.

Projection must carry two identities: retrieval passage identity and original evidence identities. Original-only projected passages may keep existing EvidenceSpan IDs for compatibility. Rendered passages use their generation/view-aware native Passage ID, and `_safe_vectors` returns entries keyed by retrieval identity with original-span mappings. It must compare the persisted and cached vector/text binding, reject profile/dimension drift, and select only authorized views. Multiple views of one span retain distinct retrieval candidates; they must not trigger the old conflicting-vector-per-span error or become duplicate source quotations.

Add explicit graph metadata or a small immutable mapping from each retrieval passage ID to its view ID (nullable), ordered original span IDs and generation ID. Carry it through GraphIndex subgraphs/merges, trace serialization and saved replay. `passage_by_id()` continues to resolve the retrieved item; callers that present evidence must separately resolve original text/locators through this mapping. Update `ask.py`, evidence-envelope/answer construction, MCP/HTML evidence rendering, evaluation replay and code-context readers accordingly. Rendered context is explicitly labeled derived. Never overwrite an original span's text to keep an existing caller working. One citation may carry multiple original spans; deduplicate by original identity without discarding the retrieval-view identity.

For each authorized extraction, build source-local inferred Entity/Fact IDs from source ID plus normalized name/triple. Do not include generation in these logical projected IDs; different selected generations replace their supported contributions. Preserve generation ownership in provenance. Deduplicate equivalent source-local triples, union only authorized contributing passage support, and require equivalent per-profile vectors rather than silently choosing among conflicting vectors. The inference input-to-passage relation comes from immutable support_passage_ids, not global Fact endpoints. Map those physical IDs to the corresponding projected original/view IDs. Count one contribution per distinct declared support passage; the coordinator must not multiply support merely because a span has extra retrieval views. The explicit mapping is sealed as extraction payload and identity, and must agree with PreparedIndex coverage.

Keep typed AssertionVersion/AssertionSupport relations on their existing separate channel. Recompute entity mentions, fact counts and allowed synonym candidates from selected authorized extractions only. Hidden/staging outputs cannot affect graph dimensions or weights. Cross-source inferred identity merging and LinkGeneration refresh remain outside this proposal.
