REQUIRED BEHAVIOR (plan section 5):
1. Frozen `TemporalPublicationPlan` in `knowledge/temporal.py`: exact closure operations (target version IDs to close at `published_at`) and the new version IDs it appends; prepared outside the write transaction; contains no callbacks; canonical, sorted, unique; validates that a target is not also a new version.
2. Inside `publish_staged_generation`, under the existing lock/fence/CAS/suppression/seal checks: every closure target exists, belongs to the same workspace and source lineage through complete support, is currently open (`recorded_to is None`), has `recorded_from < published_at`, and is not already closed differently; every appended replacement segment is an exact member of the staged generation, has `recorded_from == published_at`, and preserves assertion identity, scope and evidence dependencies; object-observation corrections obey the equivalent object/revision/span closure.
3. One transaction closes the old rows with `recorded_to = published_at` (through the store's batch closure path that reuses `update_knowledge`'s monotonic rule), appends the already-staged rows, publishes/retires generations, advances graph/content state and writes the publication event. A failpoint after any closure, pointer, event or retirement rolls everything back (use `fault_hook`); the prior publication and every open version are byte-identical afterwards.
4. Exact publication retry returns the original receipt and observes the already-applied closures; a different closure plan, stale parent or fence, later suppression epoch, or conflicting close fails without writes.
5. No model, filesystem, remote callback or unguarded clock runs inside the transaction (`published_at` comes from the plan, fixed by the caller; the store clock is used only where the existing publish path already uses it).
6. Generic fixture publication (`publish_generation` compatibility path, if any test helper uses it) must not become a bypass: a plan is honoured only by the strict path; the compatibility path rejects a generation that carries a plan.
7. `select_history` (part 1) over a corrected series at a cutoff before the correction returns the original segment; at a cutoff after it returns the corrected one; `recorded_to` is visible in serialization; the May ownership example from the plan is the canonical test.
