# Code as a first-class data type in hippo (phase 1)

Supersedes `inputs/A-existing-plan-phase1.md`. Grounded in `research/R1`–`R6`; every existing path, function, setting and route named below is cited to the research file that verified it, or marked `new`.

## Context

hippo is a portable HippoRAG: passages → OpenIE entities/facts → a graph in LadybugDB (default) or Neo4j → an in-memory igraph → Personalized PageRank → ranked passages → an LLM answer (R1.2, R3.1). The store layer is three independent implementations kept in step by convention and tests, not by an interface: `store/base.py` is the *Neo4j* backend's base class, `store/ladybug.py` is a self-contained twin, `tests/fakes/fake_store.py` is the third (R1.1, R1.12). Code already gets in — repos, zips, files — but is chunked into 1500-char line windows and run through OpenIE like prose, at two LLM calls per chunk with no skip flag anywhere (R2-2, R2-3, R2-6).

**Problem.** An engineer indexes a repository and asks a question containing code — a snippet, a stack trace, an identifier — on the Ask page, over MCP, or in an eval. hippo should return the right functions, the call path between them, the tests and the commits that touched them, and show on the Analyze page exactly why. Prose sources must keep behaving exactly as they do today.

## Design summary

### Graph model

```
Existing:  (Source)<-[:FROM]-(Passage)-[:MENTIONS]->(Entity)   (Passage)-[:STATES]->(Fact)-[:SUBJECT|OBJECT]->(Entity)
           (Entity)-[:SYNONYM {score, manual}]-(Entity)        (Entity|Passage)-[:TUNED {weight}]-(Entity|Passage)
Added:     (Symbol {id, source_id, name, qualname, kind: module|class|function|method, lang, path,
                    line_start, line_end, signature, doc, is_test, raises STRING[], community,
                    name_tokens STRING[], boost, embedding, created_at})
           (DataObject {id, source_id, name, qualname, kind: table|column|collection|label|rel_type,
                    dialect, name_tokens STRING[], boost, embedding, created_at})
           (Commit {id, source_id, sha, author, date, message, ordinal, created_at})
           (Symbol|DataObject)-[:CODE_EDGE {kind, omega, provenance, extra}]->(Symbol|DataObject)   directed
           (Commit)-[:MODIFIES {omega, hunk}]->(Symbol)          (Commit)-[:PRECEDES]->(Commit)   first-parent
           (Symbol|DataObject|Commit)-[:DEFINED_IN]->(Passage)                                    ω 1.0
           (Passage)-[:REFERS_TO {omega, token}]->(Symbol|DataObject)   prose/commit passage naming a symbol
           SYNONYM widens to (Entity|Symbol|DataObject)²      —  9 ordered pairs
           TUNED   widens to (Entity|Passage|Symbol|DataObject)²  — 16 ordered pairs
CODE_EDGE pairs: (Symbol,Symbol), (Symbol,DataObject), (DataObject,DataObject)   [table→column CONTAINS]
```

Node ids: `symbol_id(source_id, path, qualname) = make_id("symbol-", f"{source_id}:{path}:{qualname}")`, `data_id(source_id, kind, qualname) = make_id("data-", f"{source_id}:{kind}:{qualname}")`, `commit_id(source_id, sha) = make_id("commit-", f"{source_id}:{sha}")`, all in `codegraph/model.py` (`new`); the store never computes an id. `make_id` is a prefixed md5 (`hipporag/text.py:27-29`), so these namespaces are disjoint from `entity-`/`fact-`/`passage-` (R1.8).

### ω by provenance (merged table; A's values, D24)

| Edge kind | ω | provenance (stored verbatim) |
|---|---|---|
| CONTAINS (module→class/function, class→method, table→column) | 1.00 | `syntax` |
| IMPORTS | 0.95 direct path / 0.90 through `__init__` or index re-export / 0.60 wildcard | `import_path` / `reexport` / `wildcard` |
| INHERITS | 0.90 resolved / 0.50 unique bare-name match | `resolved` / `fuzzy_name` |
| OVERRIDES | 0.90 | `mro` |
| INVOKES | 1.00 same file / 0.90 via import or inheritance / 0.50 unique bare-name match | `same_file` / `via_import` / `via_inheritance` / `fuzzy_name`; `extra` JSON `{call_line, call_lines, in_branch, is_await, arg_binding}` |
| RAISES / CATCHES (function → in-repo exception class) | 0.90 | `resolved`; builtin exception names go to `Symbol.raises[]`, not an edge |
| TESTED_BY | 0.85 / 0.75 / 0.60 | `test_import` / `test_filename` / `test_mention` |
| READS / WRITES (symbol → data object) | 0.85 parsed literal / 0.60 bare identifier | `sql_literal`, `mongo_chain`, `mongoose_model`, `cypher_literal` / `bare_identifier` |
| MODIFIES (commit → symbol) | 1.00 | `hunk` (JSON: file, old/new ranges, churn) |
| REFERS_TO (prose/commit passage → symbol/data object) | 0.85 backticked or qualified / 0.60 split-token | `backtick` / `tokens` |

Calls to anything that does not resolve inside the source produce **no edge**. No cross-source edges. One `CODE_EDGE` per `(a, b, kind)`: repeated call sites keep the highest ω and the first `call_line`, with `extra.call_lines` listing the rest.

### Retrieval rule

**Edge weight** (`hipporag/graph_index.py:69-73`, R3.3): `tuned if set else max(fact_count, 1.0 if mention, synonym_score, (code_terms) × code_structural_scale)`, where `synonym_score` is the **Entity–Entity** score only and `code_terms` is the best of the pair's ω-bearing code relations *and* its cross-kind synonym score — every term that exists only because code was indexed (Ruling 2). Nothing else in the `max` is scaled. At the default scale of 1.0 an entity pair with three facts (3.0) outranks any code edge, and `SETTING_RULES` caps `code_structural_scale` at **3.0** precisely so a code edge can at most *tie* three facts, never outrank them — the fidelity sentence must not be conditionally false (V2.3). Unlike B's D2 shape these pairs carry no `Fact` rows, so ω is the only term and the scale is a live lever (R3.3-omega, R3.3-AB). **S2.3 (as amended by Ruling 2) — which relations enter igraph, and with what term. Every relation that exists only because code was indexed is multiplied by `code_structural_scale`, so scale 0 removes every code vertex from igraph (`build_igraph` keeps only `weight > 0`). `TUNED` is exempt, as it always is: a user set it.**

| Rel | In igraph? | Weight term in the `max` | Direction kept for path tools? |
|---|---|---|---|
| MENTIONS, STATES-derived fact edges, Entity–Entity SYNONYM, TUNED | yes (as today) | as today, unscaled | no |
| CODE_EDGE | yes | ω × `code_structural_scale` | yes (`code_out`/`code_in`) |
| DEFINED_IN | yes | 1.0 × `code_structural_scale` (counts as a mention) | yes |
| SYNONYM, cross-kind (Entity–Symbol, Entity–DataObject, Symbol–Symbol, …) | yes | `synonym_score` × `code_structural_scale` | no |
| REFERS_TO | yes | ω × `code_structural_scale` | yes |
| MODIFIES | yes | ω × `code_structural_scale` | yes |
| PRECEDES | **no** | — | side list only (`history` tool) |

`PRECEDES` is excluded because 200 commits would chain every symbol they touched into one undirected neighbourhood; it exists only as a `DirectedEdge`. `MODIFIES` and `REFERS_TO` being in igraph is how commit and README passages get retrieved at all.

**S2.4 — specificity is per kind, computed once in `GraphIndex.load` into the single shared array, never branched on in the retriever** (`retriever.py:286-287` keeps dividing by whatever it finds, R1 gotcha 7): the retriever *divides* by the array (`w /= index.entity_passage_count[v]`), so the array holds the **denominator**, never the reciprocal — storing `1/x` as written would invert the damping and boost hub symbols instead of damping them (V2 S2-4). Stored values: entity → number of passages that mention it; symbol and data → `in_degree + 1` counting **INVOKES, READS, WRITES only** (MODIFIES excluded, or a function changed in 150 of 200 commits would be crushed); commit → `1`; passage → `0`, never seeded. `scoped()` recomputes the same way from the visible subgraph.
- **Seeding**: lexical anchors (identifiers, stack frames at `0.8 ** k`, exceptions, fenced code, diff hunks) plus dense seeds, inserted **after the fact filter and before the DPR-fallback decision** at `retriever.py:261`, whose condition becomes `if not kept_fact_indices and not trace.used_code_seeds` (R3.1-A).
- **`used_code_seeds` = at least one *lexical anchor* seed was kept** (identifier, stack frame, exception, fenced code, diff hunk). Dense seeds add reset mass but **never** flip the gate, so they never disable the DPR fallback, trigger the select pass, write `timing["paths"]` or add the context block (Ruling 1a). And **a dense seed is admitted only when its passage is within the overall top `code_dense_seeds` of *all* passages** by `dpr_scores`, not top-N among code passages (Ruling 1b). Without both, the gate is on for every question on any memory containing code: `dpr_scores` is min-max normalised (`retriever.py:200`), so five code passages always rank top-5 among code passages whatever was asked (V2.3). Consequence, and it is the checkable one: a prose question over a mixed corpus behaves exactly as today unless a code passage out-ranks every prose passage on dense similarity — in which case it would already have been a DPR result on its own merits.
- **`link_top_k` treatment**: the cut at `retriever.py:301` (how many *entities* keep a weight) does not apply to symbol seeds; `MAX_CODE_SEEDS = 20` by weight is their own budget. The other two jobs `link_top_k` does — how many facts reach the filter (`:210`) and how far the kept list is cut (`:218`) — are untouched (R3.1).

**Sentences to add to `docs/FIDELITY.md`** (checkable form, per `FIDELITY.md:121-124`'s precedent, R3.10):

> With no code sources indexed nothing changes: no code vertex exists, and the fourth term in the edge-weight `max` is 0.0, which cannot raise a max. With code indexed, `code_structural_scale = 0` drops **every** pair that exists only because code was indexed — CODE_EDGE, DEFINED_IN, REFERS_TO, MODIFIES and cross-kind SYNONYM — out of igraph, because each is multiplied by that scale and `build_igraph` keeps only `weight > 0`; every code vertex therefore has degree 0 and cannot receive or pass PPR mass. Adding `code_seed_weight = 0` and `code_dense_seeds = 0` restores fact-only seeding and `code_select = False` removes the second LLM pass. Under those four settings a prose corpus indexed alongside code ranks identically to the same corpus indexed alone; the only surviving code-touching edge is a `TUNED` weight a user set by hand. Code passages remain ordinary passages and still receive DPR seed mass, as any passage does.

### WP2b — Git history (own PR, after WP2)

**Goal.** `Commit` nodes, `MODIFIES`, `PRECEDES` and commit-message passages for repo sources.

`read_history(checkout: Path, symbols: list[Symbol], *, depth: int, timeout_s: int, total_s: int) -> History(commits, modifies, precedes)`. `git log --first-parent -n {depth}` gives the commit list (R4 T11: 0.042 s for 200 commits) and `git show -U0 <sha>` the zero-context `@@ -a +b @@` hunk ranges (R4 T11 confirmed the format). `PRECEDES` chains consecutive first-parent commits (newest → older). Commit passages: text = `message + "\n\nTouched: " + qualnames`, title `commit {sha[:10]}: {subject}`, `defines = [commit_id]`, `extract_text = message` (OpenIE sees the message only; the ≥ 80-char rule skips one-liners, S2.7). `repos.clone_repo` hardcodes `--depth 1` with no `depth` parameter (`repos.py:58,69`, R2-7); it gains `depth: int = 1` threaded from the `code_history_depth` setting (S2.11) through `read_source`'s `kind == "repo"` branch (`pipeline.py:316-321`). Progress is a single `on_progress("reading history", 0, 1)` / `(…, 1, 1)` pair (R2-10).

**S2.9 — MODIFIES intersects each hunk with the symbol ranges AT THAT COMMIT, not at HEAD.** This reverses A's stated approximation, and the reason is that WP4.5's commit eval uses these edges as its gold labels: a HEAD-range shortcut would make the eval measure its own drift on every commit older than a few edits. Per commit, per touched file in a supported language: `git show <sha>:<path>` → parse with tree-sitter (R4 T9: milliseconds per file) → intersect the hunk's **new**-side ranges with *that* parse's symbol ranges → map each hit to the HEAD symbol by `(path, qualname)`; a symbol absent at HEAD produces no edge. `MODIFIES` ω 1.0; `hunk` JSON is `{file, old_range, new_range, churn}` through `text()`/`decode()` like `extra` (R1 gotcha 3). Rename detection (`-M`) is **off**: history before a rename is ignored in phase 1 (Known limitations). Cost is `depth × touched files` parses instead of one `git log -p`, and it is **unmeasured**: R4 T11's 0.042 s timed the *old* one-shot design, not this one. For 200 commits × ~5 files that is ~1 000 subprocesses. A per-commit budget alone is not enough — 200 × `code_git_timeout_s` is 33 minutes inside one index job — so there is also a **whole-pass** budget: `code_history_total_s` (default 120), after which history reading stops and the commits already read are kept. **S2.13 — anchor fan-out.** `n_matches` is the **pre-cap** count of everything the token matched, and the rules run in this order: count all matches → drop the token as `ambiguous` if `n_matches > 10` → otherwise seed up to `MAX_MATCHES_PER_TOKEN` of them at `code_seed_weight / n_matches`, recording `n_matches` and `matched_by` on each `SeedSymbol`. **S2.17 — `tests/fixtures/code_sample/expected.json` is checked in beside the tree and is the spec.** It lists every symbol (the three `symbol_id` inputs, kind, qualname, path, line range), every edge (`a`, `b`, kind, ω, provenance), every DataObject, every REFERS_TO and DEFINED_IN pair, and the commit→symbol MODIFIES set for the `tmp_path`-built history. **A git SHA is not reproducible** — it hashes the author and committer names, emails *and timestamps*, and `source_id` differs per run, so a file keyed on `commit_id = make_id("commit-", f"{source_id}:{sha}")` could never match (V2 S2-17). Two rules, per Ruling 5: `expected.json` keys commits by `(ordinal, subject)` and MODIFIES rows by `(ordinal, path, qualname)`, **never by SHA**, and the comparison test maps run-time SHAs through the ordinal; and belt-and-braces, `make_code_checkout` pins `GIT_AUTHOR_NAME/EMAIL/DATE` and `GIT_COMMITTER_NAME/EMAIL/DATE` to fixed values so the SHAs are stable across machines anyway. One parametrized test in **WP2's `test_indexer.py`** indexes the fixture and asserts the loaded graph equals the file, order-independent and with `community` excluded (S2.10). Every rule in S2.6-S2.9 is therefore mechanically checkable, and the file — not this document — is what a junior argues with. Regeneration is `pytest tests/unit/test_indexer.py --update-expected`, which needs a `pytest_addoption` hook in `tests/conftest.py` — **none exists today**, so that hook is itself WP2 work (V2 S2-17b); a `scripts/update_expected.py` is the equally acceptable alternative. Either way a regeneration diff is a **reviewable change to the spec**, read like a source change, never a green-the-build reflex, and the flag is refused in CI.

`place` carries a ≥ 80-char docstring so WP4's code-question generator has a qualifying function. `save` raises `OrderError` and `place` catches it, giving RAISES/CATCHES; `place`'s `raise ValueError` lands in `Symbol.raises` with no edge. Line numbers in tests are recomputed from the final files.

## Known limitations to state in the docs

- **Overrides do not survive a re-index.** `remove_orphans` deletes an `Entity` that loses its last `MENTIONS`, taking its `TUNED` and `SYNONYM` edges with it — a pre-existing bug affecting prose today, not one this work introduces (R1.3, R1.11, R3.6-sy). Code nodes are never orphan-swept, but `delete_passages_for_source` deletes them by `source_id`, so a boost or tuned weight on a symbol dies on the next re-index too. The phase-2 fix is B's `Override` table (D14) or a `prune_code_nodes(source_id, keep_ids)` sweep after write.
- **Write throughput.** R4 T8 inserted 50,000 nodes and 200,000 relationships in 537 s on this machine (0.4 s for the nodes, 536 s for the relationships), against 13.6 s for 100,000 relationships over 10,000 nodes in T5 — endpoint-lookup cost is sharply scale-sensitive for the `UNWIND` + two-`MATCH` shape both stores use. Batch size is 5,000. hippo itself is ~900 symbols; a repo large enough to approach T8's shape would hit `MAX_CHUNKS = 20_000` first (R2-8). Treat 537 s as the measured ceiling, and add a perf assertion to the fixture index if repo size grows.
- **History stops at renames.** MODIFIES now intersects hunks with the symbol ranges *at that commit* (S2.9), so line drift is no longer a source of error; but rename detection (`-M`) is off, so a symbol's history before it was renamed or moved is not attributed to it. Commits whose `git show` exceeds `code_git_timeout_s` are skipped and counted in `Source.meta.history_skipped`.
- **Cypher extraction reads literal labels and rel types only.** Indexing hippo yields `DataObject`s for `Settings`, `Passage`, `Source` from `MATCH`/`MERGE` string literals, not from the f-string-interpolated `CREATE NODE TABLE {name}(...)` declarations. "Our own databases" means Cypher literals, not schema introspection.
- **Unresolvable calls are silent in phase 1.** A call to stdlib, a third party, or a name the resolver cannot bind produces **no edge**, and only a per-file *count* in `CodeGraph.stats()` → `meta["code"]` (D15) — enough to see how big the gap is, but the `Unresolved` leaderboard that would show which names they are is phase 2.
- **The fake cannot demonstrate the noise fix.** `FakeOllama` produces almost no triples from code today, so tests can only assert the call-count reduction, not the quality improvement (R2 gotcha 4).
