1. Background

1.1 For beginners: what hippo is and why it has a graph database

Skip to 1.2 if you already know hippo.

hippo is a personal memory. You feed it text: notes, documents, an entire git repository. It reads that text with a local language model, pulls out the things mentioned and the facts connecting them, and stores those as a small knowledge graph. Later you ask a question in plain English, and hippo answers from what it remembers, showing you which facts it matched and which passages it read. It is a portable implementation of HippoRAG 2, and it also speaks MCP so tools like Claude Code can use it.

The graph is the heart of it. Suppose you index one sentence from the sample corpus:

The Orion arm was designed by Marcus Lee at Acme Robotics in Boulder.

hippo stores a Passage node holding that text, Entity nodes for orion arm, marcus lee, acme robotics, boulder, and Fact nodes for triples such as ["Orion arm", "was designed by", "Marcus Lee"]. Edges tie them together, and every passage points at the Source it came from:

Source: acme_robotics.md
Passage: "The Orion arm was designed by…"
Fact: orion arm —designed by→ marcus lee
Entity: orion arm
Entity: marcus lee
Entity: boulder
Edges (not drawn): Passage —FROM→ Source; Passage —MENTIONS→ Entity; Passage —STATES→ Fact; Fact —SUBJECT/OBJECT→ Entity. Synonyms link entities whose names mean the same thing.

Answering a question is a walk over this graph. The question Who designed the Orion arm? is embedded and compared with every fact; the best-matching facts are kept, their entities become seeds, and Personalized PageRank spreads activation from those seeds along the edges. Passages that light up most are handed to the language model, which writes the answer.

Two homes for the graph The graph lives in a database (durable, queried with Cypher) and runs in memory: hippo loads every node and edge into an igraph structure plus numpy matrices whenever a graph_version counter changes. The database is therefore mostly a persistence layer with a query language, not the thing that does PageRank.

Until this branch, that database was Neo4j: a separate Java server, run in Docker, with a password, a browser UI on port 7474 and a bolt port on 7687. It works well, but it is heavy for a "memory you run on your own machine". Starting hippo meant starting Neo4j, and running the CLI meant reaching a server.

1.2 Directly relevant: the store layer, and the work that arrived alongside

Everything hippo persists goes through one object, the store. Before this change it was hippo.store.Store, a class assembled from four groups of Cypher queries: memory.py (sources, passages, entities, facts and their links), evals.py (question sets and evaluation runs), changesets.py (saved graph edits) and base.py (connecting, settings, the version counter). Web routes, the MCP server and the CLI all receive an AppContext that holds the store, and they only ever call methods like store.add_passages(rows) or store.get_facts(ids). None of them write Cypher.

That discipline had already produced a second implementation: tests/fakes/fake_store.py, an in-memory dictionary-backed FakeStore with the same methods and row shapes. The unit tests ran against the fake locally and against a real Neo4j in CI, and a comment in the fake says: If you add a query to the real store, add it here too. This branch adds a third implementation and leans on exactly that contract.

The app only knows the store's method names. Any object with those methods will do, which is what makes a second backend feasible.

One more piece of context matters. While this branch was being built, another session was adding role-based access control and a 3D graph view to hippo's main checkout: roles on a rank ladder, users with passwords and tokens, per-source visibility, sign-in for the UI, API and MCP. That work touched the store contract in three ways. It added Role and User nodes with a new query module store/users.py; it gave every read of sources, passages, entities and facts an access argument that filters what the caller may see; and it made load_entities return created_at. The ladybugdb branch contains a snapshot of that work too, so that the new store could be proven against the full contract rather than the old one.

2. Intuition

The core idea is small: swap the database server for a database file, behind the interface that already existed. Everything else in the branch is the consequence of taking that idea seriously.

2.1 A file instead of a server

LadybugDB is the community continuation of Kùzu, an embedded property-graph database: it runs inside your Python process, speaks Cypher, and keeps everything in a single file. Think of it as "SQLite, but for graphs". Opening the store is now:

store = LadybugStore("data/hippo.lbug")   # creates the file and its tables if missing

Compare the two ways of running hippo:

before ./hippo up
app container
↔
neo4j container1 GB heap · password · ports 7474/7687
after pip install -e . && hippo serve
hippo process
↔
data/hippo.lbugone file, opened in-process
Ollama, the model server, is still needed in both cases. The database server is not.

Neo4j does not go away. It becomes an option: HIPPO_STORE=neo4j (with pip install 'hippo[neo4j]', or a Docker profile) uses the untouched Neo4j code. A single function decides:

def open_store(config):
    if config.store_backend == "neo4j":
        return Store(config.neo4j_uri, config.neo4j_user, config.neo4j_password)
    return LadybugStore(config.database_path)

2.2 Same graph, stricter dialect

The graph shape is identical in both backends, but LadybugDB is a different kind of database. Neo4j is schemaless: you can SET s.min_rank = 40 on a node that never had that property. LadybugDB wants every table and column declared first, with a type:

CREATE NODE TABLE Entity(id STRING PRIMARY KEY, name STRING, boost DOUBLE,
                         embedding FLOAT[], created_at STRING)
CREATE REL TABLE MENTIONS(FROM Passage TO Entity)

That strictness has a pleasant side effect. In Neo4j a null property simply does not exist on the node, so a source created with error: null comes back with no error key at all, and every row-shaping function has to fill defaults in. LadybugDB returns the column with None. The new store strips those Nones before handing rows to the same shaping functions, so callers see identical dictionaries from either backend.

The dialect is also smaller. Three Neo4j idioms used throughout the old queries have no LadybugDB equivalent, and each has a plain substitute:

Neo4j idiomWhat it didLadybugDB substitute
count { (e)<-[:MENTIONS]-() }count a pattern inlineOPTIONAL MATCH the pattern, then count(p) in an aggregation
SET s += $fieldsset many properties from a mapbuild the SET a = $a, b = $b list in Python from the already-validated keys
[(p)-[:STATES]->(f) | p.id]pattern comprehension into a listOPTIONAL MATCH plus collect(p.id)

Settings and free-form metadata, which Neo4j kept as arbitrary properties on one Settings node, become two JSON text columns on a single row, because a declared schema cannot grow a column per key.

2.3 The two surprises in the binding

Two behaviours of the Python binding (real_ladybug 0.15.3) shaped the code more than the dialect did. Both were found by probing, and both are documented at the top of store/ladybug.py so that the next person does not rediscover them the hard way.

Surprise 1: strings that look like JSON are parsed. Pass the parameter '{"a": 1}' and the query receives a struct, not a string. Pass '[1, 2]' and it receives a list. Inside a list-of-rows parameter, such a string becomes the empty string. hippo indexes code and JSON files, stores LLM output, and keeps several *_json columns, so this would silently corrupt data.

The workaround is to send every piece of free text as bytes, which the binding leaves alone, and to turn it back into a string inside the query with LadybugDB's decode():

self.run("MATCH (p:Passage {id: $id}) SET p.text = decode($text)",
         id=passage_id, text=text(passage_text))      # text() -> bytes or None

Ids, timestamps and fixed status words like 'ready' are safe and travel as plain strings. A test named test_text_that_looks_like_json_or_a_list_is_stored_verbatim now runs against all three stores to keep this honest.

Surprise 2: MERGE of a relationship fails under UNWIND. UNWIND $rows AS row MATCH (a), (b) MERGE (a)-[:MENTIONS]->(b) raises an internal error. Doing one MERGE statement per pair works but costs about 10 ms each, and a large source creates tens of thousands of mention links.

The substitute is "create the edge unless it exists", which LadybugDB handles in one batched statement:

UNWIND $rows AS row
MATCH (a:Passage {id: row.a}), (b:Entity {id: row.b})
WHERE NOT EXISTS { MATCH (a)-[:MENTIONS]->(b) }
CREATE (a)-[:MENTIONS]->(b)

Measured: 2,000 links in 0.03 s this way, versus 18 s one at a time. Node writes and edge writes are therefore always two statements per batch.

2.4 One process at a time, and what that means for the CLI

A server can be shared; a file cannot. LadybugDB allows exactly one process to have the file open. That is fine for hippo serve, but the CLI commands (hippo ask, hippo sources, hippo index, and the new hippo users) each start a fresh process and used to open their own store. While the server runs, they would fail.

The branch handles this in two layers:

hippo ask "…"new process
→
try to open hippo.lbugadvisory lock on hippo.lbug.lock
✗ locked →
RemoteHippoPOST /api/ask with Authorization: Bearer $HIPPO_TOKEN
→
hippo serveowns the file
If the file is free, the CLI opens it directly. If it is held and a server answers, the CLI asks the server. If it is held and nothing answers, the error names the problem.

The advisory lock exists for a subtle reason. A second process that opened a busy database did not get LadybugDB's own "locked" error; it read the write-ahead log mid-write and reported Corrupted wal file. The files were unharmed (it only reads), but the message would send someone hunting for corruption that is not there. Taking hippo's own flock on a sidecar .lock file before touching the database means a second hippo never gets that far.

2.5 Access control on the file store

The access-control work defines visibility per source. Every source records the lowest role that may see it as an integer min_rank, plus an optional owner_id. A caller's Access is their rank and user id. The Cypher predicate is one comparison, bound to a source s:

($acc_all OR s.owner_id = $acc_uid OR coalesce(s.min_rank, 0) <= $acc_rank)

Passages follow their source. Entities and facts are shared between sources, so they are visible when at least one visible passage mentions or states them, and their passage counts only count visible passages. Here is the sample corpus after an admin restricts it to rank 40, seen by an Individual (rank 0) who also added a note of their own:

Source: acme_robotics.md (min_rank 40)
Source: my-notes.md (owner: me)
Passage: "The Orion arm was…"
Passage: "Zed Labs is in Lisbon…"
Entity: orion arm (0 visible mentions)
Entity: zed labs (1 visible mention)
Fact: orion arm —designed by→ marcus lee
Fact: zed labs —located in→ lisbon
Struck-through nodes are filtered out of every store read for this caller, and cut out of the in-memory graph before PageRank runs, so activation cannot flow through them.

The LadybugDB store applies the very same predicate; only the surrounding query shape differs (an OPTIONAL MATCH … WHERE followed by an aggregation instead of a count {} subquery). A live run confirmed the behaviour end to end: the Individual asking Who designed the Orion arm? got "I have nothing in memory to answer that yet" with zero passages ranked, while the Arch admin got "Marcus Lee" with eight.

Why the contract mattered The access-control work was written for Neo4j by someone who did not know LadybugDB existed. Because it followed the rule "new store methods go into the store package, the fake, and the shared tests", giving LadybugDB parity was a contained job: read the new methods, write their LadybugDB equivalents, and run the same tests until they passed on all three backends.

3. Code walkthrough

The branch is four commits. Reading them in order tells the story: first the new store and the plumbing to select it, then a packaging fix, then the access-control snapshot with LadybugDB parity, then a re-sync with later edits. The walkthrough below is grouped by concern rather than by commit.

3.1 The new store: src/hippo/store/ladybug.py (about 1,400 lines)

One class, LadybugStore, with every method of the Neo4j Store. It reuses the Neo4j store's row-shaping helpers (_source_row, _passage_row, _result_row and so on) so that a row from either backend is built by the same function. The file opens with two schema tables:

NODE_TABLES = {
    "Source": """id STRING PRIMARY KEY, kind STRING, name STRING, status STRING, ...
                 owner_id STRING, access_role_id STRING, min_rank INT64""",
    "Passage": "... embedding FLOAT[], entities_json STRING, ...",
    "Role":    "id STRING PRIMARY KEY, name STRING, rank INT64, ... capabilities STRING[], builtin BOOLEAN",
    "User":    "id STRING PRIMARY KEY, username STRING, ... token STRING, role_id STRING, disabled BOOLEAN, ...",
    ...
}
REL_TABLES = [("FROM", "FROM Passage TO Source", ""), ("MENTIONS", "FROM Passage TO Entity", ""),
              ("TUNED", "FROM Entity TO Entity, FROM Entity TO Passage, FROM Passage TO Entity, FROM Passage TO Passage",
                        ", weight DOUBLE, updated_at STRING"), ...]

Points worth noticing as you read it:

  • Opening. __init__ takes the advisory lock, opens the database, creates a connection, and runs ensure_schema() (all CREATE … IF NOT EXISTS). A lock failure raises StoreLockedError with advice; a WAL error is re-raised with a hint that an older hippo may hold the file.
  • Running queries. run() holds one RLock around every statement, because LadybugDB allows one writer at a time within the process. Rows come back as dicts keyed by column alias; whole nodes pass through _node(), which drops internal _ID/_LABEL keys and None values.
  • Text. The text() helper encodes free text to bytes; every such parameter is wrapped in decode() in the query. The generic _set() helper builds a SET list and applies the same rule to string values automatically.
  • Links. _link(rel, from_label, to_label, pairs) is the batched create-unless-exists helper; add_passages, add_facts, link_passage_entities and link_passage_facts all go through it. add_synonyms is two statements: update existing edges, then create the missing ones.
  • Order. Neo4j's UNWIND $ids … MATCH returns rows in the order asked; LadybugDB's WHERE id IN $ids does not. _in_asked_order() restores it for get_passages, get_entities and get_facts.
  • Access. _SOURCE_QUERY, _VISIBLE_MENTIONS and _fact_rows carry the shared ACCESS_WHERE, and every affected method gained the access parameter with access_params(access) binding the three $acc_* values.
  • Users and roles. The whole of UserQueries is mirrored: role seeding on first connection, editable roles whose rank change is copied onto their sources, users with scrypt password hashes and bearer tokens, set_source_access. Users reference roles by role_id; there is no HAS_ROLE edge. Username and token uniqueness is checked in Python, since LadybugDB only enforces primary keys.

3.2 Choosing a backend: config.py, store/__init__.py, context.py

Config gains store_backend (from HIPPO_STORE, default ladybug, validated against the two allowed values) and db_path (from HIPPO_DB_PATH, defaulting to <data_dir>/hippo.lbug), plus two properties: database_path and a human-readable store_location. The store package exports open_store(config) and a type alias AnyStore = Store | LadybugStore; AppContext.from_env() calls open_store instead of constructing Store directly. The Neo4j driver import in base.py moved inside Neo4jBase.__init__, so the package loads without the driver installed and gives a clear message if you ask for Neo4j without it.

3.3 Status and pages: status.py, two templates

The status dictionary now reports store (up or not), store_backend and store_location; the old neo4j key stays as an alias for anything already reading /api/status. The header pill reads "Graph" with the file path as its tooltip, or "Neo4j" with the bolt URI when that backend is chosen. The Settings page shows either the Neo4j card with its browser link or a card describing the embedded file and how to back it up.

3.4 The CLI and its remote fallback: cli.py, remote.py

RemoteHippo is a thin httpx client for /api: ask, sources, settings, upload and repo indexing with polling, and the users and roles endpoints. It reads HIPPO_TOKEN and sends it as a bearer token; a 401 becomes a RemoteError whose message says to set the token from the Account page. is_up() treats a 401 as "up", since a server that wants a token is still a server.

In cli.py, one helper decides the mode for every data command:

def _context_or_running_server():
    try:
        return AppContext.from_env(), None          # we can open the file ourselves
    except StoreLockedError:
        remote = RemoteHippo.for_config(load_config())
        if not remote.is_up():
            raise                                    # locked and nobody answers: say so
        return None, remote                          # the server has it: ask the server

ask, sources, settings, index, users and user add|token|role|remove each have a local path and a remote path producing the same output. One asymmetry is deliberate: hippo user token alice without --new cannot work remotely, because the server never repeats an existing token; the command says so and points at --new.

3.5 Tests: conftest.py and the new test files

The store fixture now chooses by HIPPO_TEST_STORE: ladybug (the default, a real embedded database in a temporary file per test), fake, or neo4j (a real server at NEO4J_URI, emptied before each test). The whole suite, not just the store tests, runs against whichever is chosen. New tests cover JSON-looking text on every backend, persistence across close and reopen, the cross-process lock (a subprocess tries to open the same file), backend selection from the environment, the CLI's server fallback with and without a token, and the remote user commands. CI runs the suite three times.

3.6 Packaging and docs

  • pyproject.toml: real_ladybug>=0.15.3,<0.16 is a hard dependency, pinned to the minor version the two workarounds were written against; neo4j moves to an optional extra and into the dev extras.
  • docker-compose.yml: only the app service starts by default; ollama and neo4j are profiles. The app no longer depends_on Neo4j (it already coped with Neo4j coming up late). The Docker image installs the neo4j extra so either backend works in a container.
  • ./hippo launcher: the random-password dance and the Neo4j browser URL only happen when .env says HIPPO_STORE=neo4j; ./hippo <cli command> forwards HIPPO_TOKEN into the container.
  • README, .env.example, docs/MCP.md, docs/CONTRACTS.md: the pip-and-Ollama path is the headline, Docker and Neo4j are sections, and the single-process rule is spelled out (stdio MCP only works while the server is not running on the same file).

3.7 What came along from the other session

For completeness, the snapshot merged in from the access-control session adds access.py (roles, Access, Principal, password hashing, tokens), store/users.py (the Neo4j queries), web/auth.py (sessions, bearer tokens, the gate), routes and templates for users, account, login, forbidden and the 3D graph (routes/graph.py, static/graph.js, a vendored 3d-force-graph), and AppContext.graph_for(access), which cuts the in-memory graph down to a caller's visible sources and caches the result. Those files are theirs; this branch's contribution is that they run unchanged on LadybugDB.

Merge note That snapshot was taken from uncommitted work in main's checkout while the other session was still active. When it commits, merge main into ladybugdb first; identical hunks merge cleanly and only edits made after the re-sync need attention.
