# The design behind hippo's code graph

Two documents designed this feature before any of it was written:

* [code-only-design.md](code-only-design.md) — the design for a code graph on its own terms:
  what a symbol graph is for, what an edge has to earn to exist, and how you tell whether it is
  working.
* [code-hipporag-design.md](code-hipporag-design.md) — the same thing set against HippoRAG:
  which parts of the retrieval algorithm the code graph rides on, and which it must not touch.

They are the *why*. This page is the *where*: one row per principle, saying which module carries
it in hippo today, and — where phase 1 deliberately stopped short — what was left for phase 2 and
on what evidence. The full argument for each cut is in the Decision Log of
[`docs/plans/hippo-for-code/PLAN.md`](../plans/hippo-for-code/PLAN.md), which cites the research
file that settled it; the D-numbers below are that log's row numbers.

Read this page with [`../CONTRACTS.md`](../CONTRACTS.md) (what each module exposes) and
[`../FIDELITY.md`](../FIDELITY.md) (what stays identical to the HippoRAG reference, and adaptation
15, which is the code graph's entry there).

## Where each principle lives

| Principle | Where it lives in hippo |
| --- | --- |
| **A symbol is a first-class node, not a phrase.** A function is a thing with a path, a line range and a signature, distinct from an OpenIE phrase that happens to spell it. | `Symbol`, `DataObject` and `Commit` get their own node tables and their own id namespaces (`symbol-`, `data-`, `commit-` — `codegraph/model.py`), written by `store/code.py` and its twins on all three backends. They are *not* `Entity` rows with a `kind` column: an entity with no `MENTIONS` is swept by `remove_orphans`, and a symbol has no mentions (D1). |
| **Structure comes from a parser, not from a language model.** What a function calls is a fact about the syntax; asking a model to guess it buys noise at two calls a passage. | `codegraph/` — tree-sitter for Python and TypeScript/JavaScript, sqlglot for SQL. Pure: stdlib, tree-sitter, sqlglot and `hipporag.text`, no store and no model. The model's only job over code is a docstring of 80 characters or more, a README, or a commit message. |
| **Every edge carries a confidence, and the confidence means something.** An edge the resolver *proved* and an edge it *guessed from a unique name* are not the same edge. | Every `CodeEdge` has an `omega` (0-1) and a `provenance` naming the rule that earned it: `syntax`, `import_path`, `reexport`, `same_file`, `via_import`, `via_inheritance`, `mro`, `resolved`, `fuzzy_name`, `wildcard`, `sql_literal`, `bare_identifier`, and the rest. `code_theta` (default 0.5) is the floor the path tools and the answer block apply; PPR never sees it. |
| **Precision over completeness, and the gap is measured.** An edge that cannot be justified is not written at all. | A call into the standard library, a third-party package or an unbindable name emits **no edge**. It is counted per file into `CodeGraph.unresolved_calls`, so `meta["code"]` says how big the gap is (D15). |
| **Structure is edge weight, not a fact row.** | Structural relations are their own `CODE_EDGE` rows, not `Fact` rows. Written as facts they would land in `fact_embeddings` and compete for the fact-filter slots on *every* question, prose included, and — at a count of 1 per call — the confidence could never exceed the fact count, so ω would be invisible to PPR (D2). |
| **PPR is the expansion operator; nothing else moves.** The code graph adds vertices and weights to the graph the search already runs on, rather than a second retrieval path beside it. | `GraphIndex` gains three vertex kinds in one shared vertex space, and `personalized_pagerank(...)` is called character-for-character as before (`docs/FIDELITY.md`). Direction is kept *outside* igraph, in `code_out`/`code_in`, because PPR is undirected and must stay so. |
| **The model filters; it never authors a query.** | Unchanged: the fact filter is the reference's DSPy program. Nothing anywhere generates Cypher, a graph query or a path expression from a model reply — the path tools are ordinary graph walks over `GraphIndex`. |
| **Prose keeps behaving exactly as it does today.** | `code_structural_scale` multiplies *every* weight term that exists only because code was indexed, so at 0 no code vertex reaches igraph at all. With that plus `code_seed_weight = 0`, `code_dense_seeds = 0` and `code_select` off, a mixed memory ranks a prose question identically to the same prose indexed alone. That is a test, not a claim (D22, and the inertness paragraph in `docs/FIDELITY.md`). |
| **Overrides are data.** A person's correction to the graph is a saved, replayable, applicable thing. | As it already was: `analysis/changesets.py` (`set_setting`, `set_edge_weight`, `add_synonym`, `set_node_boost`), widened so a symbol or data object id is accepted wherever an entity id was. Phase 1 stops there — see D14 below. |
| **Seeding from what an engineer actually types.** A question with a stack trace, an identifier or a pasted snippet in it should start the search *there*. | `hipporag/anchors.py` — identifiers, stack frames, exception names, fenced blocks and diff hunks, resolved against `GraphIndex.name_index`. <!-- verify against WP3 --> |
| **Deterministic path queries, not a shortest path for display.** "How does A reach B", "what breaks if I change this", "where can this exception come from". | `hipporag/paths.py`, over `code_out`/`code_in` at `code_theta` — reached from the answer block, the API, MCP and the CLI. <!-- verify against WP3/WP4a --> |
| **Evals derived from git, not written by hand.** | `evals/question_maker.py` generates code and commit questions; a commit's `MODIFIES` edges are the gold labels for a localization eval, which is why they intersect each hunk with the symbol ranges *at that commit* rather than at HEAD. <!-- verify against WP2b/WP4c --> |

## What phase 1 defers, and why

Each of these was designed, costed and cut on the record. None was forgotten.

| Deferred | What it would be | Why not in phase 1 |
| --- | --- | --- |
| **CCG slice artifacts** (D12) | A statement-level control/data-flow graph per function, sliced at answer time so the model reads only the statements that matter. | One new module (~300 lines), a column on three stores, an answer-time slice call. Splitting an oversized body at its own top-level statements already bounds what a passage costs, which was the reason the slices were wanted. No new dependency and no model cost, so it stays cheap to add later. |
| **Incremental re-indexing** (D13) | Re-index only the files a `git diff` says changed, and patch the graph rather than rebuilding it. | There is nothing to build on: a passage row carries no path, hash or commit sha, so nothing can say which passages a changed file owns. It needs new columns on three stores, a reverse reference index, and a full-vs-changed-only CI gate to prove the two agree. Phase 1 re-indexes a source wholesale. A partial hook exists already: `Chunk.defines` → `DEFINED_IN` → `Symbol.path` gives passage → path for every parsed file, with no new column. |
| **Overrides that survive a re-index** (D14) | An `Override` table, re-applied after each index run, so a boost or a hand-set edge weight outlives the source it was set on. | Re-indexing deletes a source's code nodes by `source_id` and writes them fresh, so a symbol's boost dies with them. Prose has the same hole for its own reason (`remove_orphans` sweeps an entity that loses its last mention, taking its tuned and synonym edges) — a pre-existing bug, not one the code graph introduced. Stated in the README's Known limitations rather than quietly fixed for code only. |
| **The unresolved-reference leaderboard** (D15) | `Unresolved` and `BindingRule` tables, a page listing which names the resolver most often fails on, and changeset ops to bind them by hand. | Two node tables on three stores, a new analysis module, a page tab, two changeset ops. Phase 1 keeps the *counts* — a few lines that give phase 2 a baseline and give you a graph-health number now — but not the names. |
| **The golden-set replay gate** (D16) | Replay a saved eval set against a proposed graph change and refuse the change if recall regresses. | Cheap when it comes: the stored trace, `trace_from_dict` and `replay_filter` all exist. It is a new loop over `Retriever.retrieve`, not over the eval runner (which calls the answerer and the judge and has no filter parameter), plus a new exception type for the 409. |
| **LSP resolvers** (D23) | pyright and tsserver behind the resolver, upgrading `fuzzy_name` 0.50 edges to `resolved` 0.90. | Heavy dependencies for a drop-in adapter behind the existing `Resolution` return, with no schema change. It is also not hot-swappable: it rewrites the ω and provenance of existing edges, so it only takes effect after a full re-index. The in-house resolver already reaches the 0.90 tier for everything it can bind. |
| **Intent classification with typed restart** | Classify a question ("where is this defined", "what calls this", "why did this change") and restart PPR from a different vertex kind per intent. | Every mechanism it needs exists — `phrase_weights` is per-vertex, so any kind can carry reset mass — but nothing yet says which intents are worth distinguishing. That is a question for an eval set, and the eval set is what phase 1 builds. |
| **`Field` nodes, `READS_FIELD` / `WRITES_FIELD`** | Column-level data access: not just "this function touches `orders`" but "it writes `orders.status`". | Columns exist as `DataObject`s already (a table `CONTAINS` its columns, from DDL), but a function is linked to the table, not the column. Multiplies the data-access edge count by the width of every table for a gain nothing has asked for yet. |
| **`Repo` and `Directory` nodes, `DECORATED_BY`** | More structure above and beside the symbol. | A directory is already recoverable from `Symbol.path`, and a repository is the `Source` row. Nodes that carry no information the graph does not already hold. |
| **Cross-source edges** | A symbol in one indexed repository linked to a symbol in another. | Ids are namespaced by `source_id` precisely so a source can be deleted or re-indexed without touching another. A cross-source edge would break that; the design would have to say what happens to it when one side is deleted, and it does not. |
| **Languages beyond Python, TypeScript/JavaScript and SQL** | Go, Rust, Java, and the rest. | Each is a grammar, a walker and a resolver — the resolver being the expensive half. Unsupported languages keep today's line-window treatment and get no code edges, which is "unsupported rather than half-supported" applied to the graph: a Go file is still indexed, still searchable, and never has a wrong call edge. |
| **PR, ticket, PRD and monitor nodes; external DDL** | The rest of an engineering organisation's context. | Out of scope by decision, not by cost: the corpus is source code repositories and nothing else — source files, tests, in-repo docs and git history. Data-access edges are kept because they come from the repository's *own* literals; ingesting a schema from outside it does not. |
